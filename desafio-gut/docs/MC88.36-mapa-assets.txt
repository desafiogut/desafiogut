ACHADOS QUE MUDAM O PLANO
================================================================================

A1 — `celebration.webm` é pedido DEPOIS do paint (2907 ms vs 2114 ms).
     Removê-lo do arranque poupa 2,26 MB de I/O e memória, mas NÃO PODE reduzir
     o tempo de paint. O ganho de ≥200 ms tem de vir dos segmentos 2 a 5.

A2 — `celebration.webm` NÃO é um preload perdido: está a ser legitimamente
     montado. `EdicaoCard.jsx:100` passa `mood="celebrating"` sempre que a
     edição está `encerrada`, e o endpoint /edicoes devolve várias edições
     RELAMP-* com `status:"encerrado"`. Três cartões encerrados = três vídeos
     de 2,26 MB. A premissa do plano ("só carregar quando uma celebração for
     ativada") não se aplica: para o código, ELA ESTÁ ativada. O que é preciso
     é adiar a montagem, não condicioná-la a um evento que já ocorreu.

A3 — `background-desktop.webp` NÃO vem do <video>. O `BackgroundCanvas.jsx`
     já monta apenas o vídeo da largura corrente desde o MC88.31. O pedido vem
     de `globals.css:261`: a `<div className="gut-bg-layer--desktop">` é sempre
     renderizada (linha 87) e o CSS esconde-a com `opacity: 0` — mas um elemento
     com opacity:0 continua a descarregar o seu background-image.
     Correção coerente com o precedente do MC88.31: não montar a div.

A4 — As fontes são carregadas em DOIS sítios, com listas DIFERENTES:
       index.html:33   → Orbitron + Inter + JetBrains Mono   (<link>, bloqueante)
       globals.css:2   → Montserrat + Inter + JetBrains Mono (@import)
     O `@import` dentro do CSS é pior: só é descoberto depois de o CSS ser
     descarregado e analisado, portanto serializa mais um salto.

A5 — MONTSERRAT É PESO MORTO. Definida em `--font-display` (globals.css:69) e
     na classe `.font-display` (globals.css:449), mas NENHUM .jsx usa qualquer
     das duas. São 6 pesos + 1 itálico carregados para nada, no caminho crítico.
     (Orbitron, Inter e JetBrains Mono são realmente usadas — verificado.)
