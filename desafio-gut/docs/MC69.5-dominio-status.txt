3. PLANO DE CONFIGURAÇÃO PARA E-MAIL COM RESEND (proposta — NÃO executado)
================================================================================

PRÉ-REQUISITO 0 — Confirmar a base (operador):
   - Confirmar que desafiogut.com.br está de fato comprado e ATIVO.
   - Descobrir o REGISTRAR e ter acesso ao painel de DNS dele.
   Esforço: 10 min (login no painel do registrar). Bloqueante para todo o resto.

DECISÃO DE ARQUITETURA DE DNS (escolher UMA):
   Opção A — DNS no registrar (ex.: Registro.br): mais simples, sem mexer em NS.
   Opção B — DNS no Cloudflare (reaproveita o WAF planejado MC4/MC6): move os
             nameservers para o Cloudflare e adiciona lá todos os registros.
   Recomendação: se o WAF Cloudflare for prioridade, ir de Opção B (unifica DNS+WAF).
                 Caso contrário, Opção A é o caminho de menor atrito para só e-mail.

PASSO 1 — Adicionar/verificar o domínio no Resend
   - Criar conta/projeto Resend; "Add Domain" → desafiogut.com.br.
   - Resend gera os registros a publicar (ver Passo 2).
   Esforço: 10 min.

PASSO 2 — Publicar os registros DNS que o Resend exige (no DNS escolhido)
   Registros típicos do Resend (os valores exatos vêm do painel Resend):
     - TXT  (SPF)   → em geral incluir "include:amazonses.com" no SPF (Resend usa SES).
                      Ex.: `v=spf1 include:amazonses.com ~all`
     - CNAME (DKIM) → 3 CNAMEs `resend._domainkey` / `*_domainkey` apontando p/ Resend.
     - TXT  (DMARC) → `_dmarc` → ex.: `v=DMARC1; p=none; rua=mailto:dmarc@desafiogut.com.br`
                      (começar com p=none para monitorar; endurecer depois).
     - (Opcional) MX de retorno/return-path conforme instruções do Resend.
   ⚠️ SPF: manter UM único registro SPF combinando todos os remetentes.
   Esforço: 20-30 min de publicação + até 48h de propagação.

PASSO 3 — Aguardar propagação e confirmar verificação no Resend
   - Resend marca o domínio como "Verified" quando lê os registros.
   - Validar com `dig TXT desafiogut.com.br` / `dig CNAME resend._domainkey....`.
   Esforço: passivo (minutos a 48h).

PASSO 4 — Integrar o envio no backend (Netlify Functions)
   - Criar var de ambiente RESEND_API_KEY no Netlify (segredo — operador insere).
   - Definir remetente, ex.: "DesafioGUT <no-reply@desafiogut.com.br>".
   - Nova função (ex.: netlify/functions/enviar-email.mjs) usando o SDK do Resend.
   ⚠️ Isto é CÓDIGO — fica para o MC69.6 (fora do escopo deste MC de diagnóstico).
   Esforço: 1-2h de implementação + testes.

PASSO 5 — (Opcional) Recepção de e-mail (suporte@desafiogut.com.br)
   - Resend é foco em ENVIO; para RECEBER, usar redirecionamento/mailbox:
     • Cloudflare Email Routing (grátis) → encaminha suporte@ p/ Gmail do operador; OU
     • serviço de mailbox (Zoho Mail grátis, Google Workspace pago).
   - Requer MX próprios (conflita com "return-path" do Resend? não — MX é para
     recepção; Resend usa subdomínio/return-path para envio). Planejar com cuidado.
   Esforço: 20-30 min (Cloudflare Email Routing) + propagação.

PASSO 6 — (Opcional) Domínio customizado no site
   - Se quiser servir o site em https://desafiogut.com.br (hoje é só o *.netlify.app):
     apontar CNAME/A conforme Netlify (ou proxied Cloudflare) + custom domain no Netlify.
   - Independente do e-mail, mas costuma ser feito junto. Ver checklist Cloudflare WAF.
