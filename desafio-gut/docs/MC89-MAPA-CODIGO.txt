1. IDENTIDADE E AUTORIZAÇÃO — COMO O SISTEMA RECONHECE UM ADMIN HOJE
================================================================================
Tudo é por ENDEREÇO DE CARTEIRA. Não há e-mail em lado nenhum da cadeia.

  auth-user.mjs        prova de posse da carteira por assinatura EIP-191 sobre
                       `DESAFIOGUT-AUTH:<ts>:<endereco>` → JWT `user-session`
                       com as claims { endereco, tipo }. TTL 24h.
                       ⚠️ NÃO há e-mail no token. Nenhum.

  _lib/admin-helpers   getAdminAddresses() = Blob `admin-list:admins`
                       ∪ resolverCoordenacao(). Cache 60s.
                       resolverCoordenacao() lê env COORDENACAO_ADDRESS.

  _lib/admin-auth      autenticarAdmin(req): Bearer admin-JWT (15 min) OU
                       x-admin-token legado. Refresh rotacionado de 7 dias,
                       hash SHA-256 em Blob `admin-refresh:{endereco}`, máx. 5
                       sessões, revogação imediata (logout-all).
                       Revalida a lista a CADA pedido → remover um admin corta
                       o acesso mesmo com JWT dentro do TTL.

  _lib/rbac.mjs        getRole() → "admin" | "cliente" | "user", hierarquia e
                       requireRole(). Cache 5 min.

  auth-admin.mjs       login (EIP-191 + ADMIN_TOKEN legado) / refresh / logout.

  _lib/require-mfa     existe; o payload do JWT expõe `mfa_verified`.

VERIFICADO EM PRODUÇÃO (sonda a admin-list?endereco=, 2026-07-29):
    0xFea436…1E67  isAdmin=true   role=admin  fonte=admin-list

4. O GUTO ADMIN — JÁ É UM EXECUTOR
================================================================================
chatbot.mjs tem um ROTEADOR DE INTENTS que corre ANTES do RAG, com tabela
declarativa de gates. Os intents de perfil admin, hoje:

  criar_edicao_wizard · criar_edicao · listar_edicoes · encerrar_edicao ·
  auditoria · memoria · panic · unpanic · relatorio_indicacoes ·
  relatorio_compras · simular_vencedor · pulso_edicao · dados_mercado

  gate:  ehAdminPerfil / ehCorpOuAdmin      (declarativo, por intent)
  rl:    intents mutantes passam por aplicarRateLimit("guto-admin", 5/min)
  log:   as ações escrevem em `log-decisoes`

  detectarPerfil(req) → "visitante" | "comum" | "corporativo" | "admin".
  O ramo admin usa confirmarAdminChat: admin-JWT, x-admin-token, OU
  user-session cujo endereço esteja em admin-list. Fonte de verdade sempre no
  backend — o cliente nunca envia o seu papel.

  ⚠️ NÃO há function calling do LLM. chamarLLM() é uma chat completion simples
     (DeepSeek, OpenAI-compatível): sem `tools`, sem `tool_calls`. O modelo
     nunca executa nada — quem executa é o roteador determinístico.
     Isto é uma FORÇA, não uma lacuna. Ver a recomendação no S3.

   cotas / saldo_rs / lances. Logo:

                                (exige PRIVY_APP_SECRET, que NÃO está no

   pôr um número errado no ecrã de quem decide. É preciso escolher a definição
   ANTES de construir o painel.

7. O E-MAIL ADMdesafiogut@gmail.com — O PROBLEMA E A SAÍDA
================================================================================
O PROBLEMA: nada no backend conhece e-mails. A autorização é sobre um endereço
provado por assinatura EIP-191. Um e-mail não assina nada.

Fazer o e-mail autorizar exigiria verificar o ID token do Privy no servidor
(PRIVY_APP_SECRET, ausente) e confiar num identificador que o utilizador não
prova possuir criptograficamente a cada pedido — mais frágil do que o que já
existe, e código novo em toda a cadeia.

A SAÍDA, que não custa código nenhum:
  1. o operador entra UMA vez na app com ADMdesafiogut@gmail.com (Google);
  2. o Privy cria/recupera a carteira embutida dessa conta e a app mostra o
     endereço;
  3. esse endereço é acrescentado à lista com o POST que JÁ existe:
        POST /.netlify/functions/admin-list
        { "acao": "adicionar", "endereco": "0x…" }
     (gated por x-admin-token — operador, R5)

  A partir daí, entrar com aquele e-mail dá o painel de admin, porque o e-mail
  é COMO SE ENTRA e o endereço é O QUE AUTORIZA. É exatamente o modelo que o
  sistema já tem, e é mais seguro do que o pedido.

  Efeito colateral bom: passa a haver um segundo admin além da coordenação —
  hoje a lista persistida está vazia e a coordenação é a única. Um segundo
  admin é também a rede de segurança contra ficar trancado de fora.
