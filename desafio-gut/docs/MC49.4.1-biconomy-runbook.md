## 1. Contexto — por que `local-key` NÃO funciona e Biconomy é o caminho certo

`/health` de produção mostra `SIGNER_BACKEND:"local-key"`, `SIGNER_READY:"MISSING"`.
Setar `COORDENACAO_PRIVATE_KEY` **não resolve**, porque a verificação on-chain confirmou:

- A `coordenacao()` do contrato **live** `0x59A73Acc8E8B210C874B0E3A9eC9B8B64847F6D5` **já
  é uma Biconomy Smart Account V2** (ERC-4337): `0xdEbe637d7f74C4bfe71263920F68589f0c672D92`
  (EntryPoint v0.6 `0x5FF1…2789`, impl `0x0000002512…`, `VERSION 2.0.0`, financiada ~0.049 ETH).
- O backend `local-key` assina a partir de uma **EOA**. `verificarCoordenacao()`
  (`_lib/contract.mjs:118-119`) exige `signer.address == coordenacao()`. Uma EOA **nunca**
  iguala o endereço de um contrato → lançaria `"wallet X não é coordenacao do contrato Y"`
  mesmo COM a chave. **Local-key é arquiteturalmente incompatível com este contrato.**
- A transferência on-chain da coordenação para a Smart Account **já foi feita** (o passo
  caro). O que falta é **configuração de ambiente** para o backend `biconomy` reconstruir
  a MESMA Smart Account e assinar UserOperations.

**Owner da Smart Account (módulo ECDSA `0x0000001c…`) = EOA `0xAEFe11EDBb32fb6727693e5994a51df8ADb5EdFF`.**
O `KMS_KEY_ID` a usar **tem de derivar exatamente para este endereço** — senão a SA
reconstruída difere e a validação falha.

## 2. Pré-requisitos (GATE — não avance sem os 3 ✅)

| # | Pré-requisito | Como confirmar |
|---|---|---|
| 1 | `KMS_KEY_ID` existe em `production` | `netlify env:list --context production` (procurar a CHAVE) |
| 2 | `BICONOMY_BUNDLER_URL` existe em `production` | idem |
| 3 | `KMS_KEY_ID` deriva para `0xAEFe11ED…EdFF` | verificação KMS (Passo 2.3 abaixo) |

> ⚠️ **`netlify env:list` pode imprimir VALORES** conforme a versão do CLI. Rode-o você
> mesmo, na sua shell, e **não cole a saída bruta no chat** (R10). Basta confirmar
> presença/ausência das chaves. `KMS_KEY_ID` (ARN) e `BICONOMY_BUNDLER_URL` contêm uma
> API key embutida — trate ambos como sensíveis.

### 2.1 — Listar as envs relevantes (presença, não valor)

```bash
netlify env:list --context production
# Confirmar existência de: KMS_KEY_ID, BICONOMY_BUNDLER_URL, SIGNER_BACKEND,
#                          COORDENACAO_PRIVATE_KEY, KMS_PROVIDER (opcional, default 'aws')
```

### 2.2 — Confirmar que o bundler responde (rede correta = Sepolia)

```bash
# Substitua $BICONOMY_BUNDLER_URL pela URL real (na sua shell; não cole no chat)
curl -s -X POST "$BICONOMY_BUNDLER_URL" -H 'content-type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_chainId","params":[]}'
# Esperado: {"jsonrpc":"2.0","id":1,"result":"0xaa36a7"}   (0xaa36a7 = 11155111 = Sepolia)
```

### 2.3 — (recomendado) Confirmar que o KMS deriva para o owner certo

O endereço Ethereum derivado da chave KMS **tem de ser** `0xAEFe11ED…EdFF`. Confirme por
uma das vias, sem expor a chave:

- Console AWS KMS → a chave `KMS_KEY_ID` → derivar o endereço (public key secp256k1 →
  keccak → últimos 20 bytes), OU
- Rodar o helper interno do projeto que usa `_lib/kms-signer.mjs` para imprimir **apenas o
  endereço** do owner (a chave privada nunca sai do KMS).

Se **não** bater `0xAEFe11ED…EdFF`, **pare** — a `KMS_KEY_ID` aponta para a chave errada.

## 3. Passos da migração (operador)

> **Ordem importa.** Não faça o Passo 3.1 antes do GATE §2 estar ✅, senão o `/health`
> fica `MISSING` e toda assinatura passa a lançar erro de config do backend biconomy.

### 3.1 — Definir o backend Biconomy

```bash
netlify env:set SIGNER_BACKEND "biconomy" --context production
```

### 3.2 — Remover a chave bruta (o guard biconomy REJEITA se ela existir)

`assertChaveBrutaAusenteEmMainnet()` (`_lib/signer.mjs:76-82`) lança se
`COORDENACAO_PRIVATE_KEY` coexistir com `SIGNER_BACKEND=biconomy`.

```bash
# Remover em production (e no legado, se aplicável)
netlify env:unset COORDENACAO_PRIVATE_KEY --context production
# (se existir a variante legada) netlify env:unset COORDENACAO_PRIVATE --context production
```

### 3.3 — (se necessário) Garantir `KMS_PROVIDER`

Default do código é `aws`. Só defina se usar outro provider suportado
(`aws|turnkey|fireblocks`) — apenas `aws` está implementado em `_lib/kms-signer.mjs`.

```bash
# Opcional (default já é aws):
# netlify env:set KMS_PROVIDER "aws" --context production
```

### 3.4 — Redeploy (as functions só releem env num novo deploy)

```bash
netlify deploy --build --prod --message "chore(mc49.4.1): migrar para Biconomy em Sepolia"
# Alternativa: painel Netlify → "Clear cache and deploy site"
```

### 3.5 — Validar `/health` (Gate 0)

```bash
curl -s "https://silly-stardust-ca71bc.netlify.app/.netlify/functions/health" \
  | tr ',' '\n' | grep -E "SIGNER_BACKEND|SIGNER_READY|CHAVE_BRUTA"
```

**Esperado:**
```
"SIGNER_BACKEND":"biconomy"
"SIGNER_READY":"set"
"CHAVE_BRUTA_EM_MAINNET":"ok"
```
- `SIGNER_READY:"set"` ⇔ `KMS_KEY_ID` **e** `BICONOMY_BUNDLER_URL` presentes (`health.mjs:14-16`).
- Se ficar `MISSING`: falta uma das duas envs → volte ao GATE §2.

## 5. Rollback

⚠️ **Reverter para `local-key` NÃO restaura o crédito** enquanto a `coordenacao()`
on-chain for a Smart Account (§1) — `local-key` continuaria a falhar em
`verificarCoordenacao()`. O rollback de env abaixo serve apenas para **sair de um estado
biconomy mal configurado** e voltar ao erro conhecido/inócuo (débito com reembolso).

```bash
netlify env:set SIGNER_BACKEND "local-key" --context production
# (reintroduzir a chave só se for mesmo operar em local-key — mas ver aviso acima)
# netlify env:set COORDENACAO_PRIVATE_KEY "0x..." --context production
netlify deploy --build --prod --message "rollback(mc49.4.1): voltar SIGNER_BACKEND=local-key"
```

**Rollback real (restaurar crédito via local-key)** exigiria **reverter a coordenação
on-chain** para uma EOA (nova tx de transferência de coordenação no contrato live) — maior
superfície que concluir o Biconomy. Não recomendado se KMS/bundler existirem.
