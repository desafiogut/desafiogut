2 · ALTERAÇÕES (commit b436960)
--------------------------------------------------------------------------------
  NOVO  src/lib/sentryLazy.js
        Importa `@sentry/react` dinamicamente e faz o init. A configuração
        (scrub argon2id no beforeSend, addEventProcessor com o contexto de
        referral, privyTokenExists) veio do main.jsx INTACTA.
        Até o SDK subir, `captureException` / `captureMessage` / `addBreadcrumb`
        ENFILEIRAM em memória (limite de 50 eventos) e a fila é drenada no init.
        Expõe `sentryPronto()` e `sentryEstado()`.

  EDIT  src/main.jsx
        · `Sentry.init()` removido.
        · <Sentry.ErrorBoundary> substituído por um `RaizErrorBoundary` local
          (classe própria, mesma UI de fallback) que reporta via sentryLazy.
        · Os listeners globais de error/unhandledrejection passam a enfileirar,
          mas SÓ enquanto `!sentryPronto()` — depois de inicializado o SDK
          instala os seus próprios handlers globais, e capturar aqui também
          duplicaria cada evento.
        · Deixou de importar "@sentry/react".

  EDIT  src/lib/webVitals.js
        Passa a usar o wrapper. ⚠️ A subscrição aos Core Web Vitals CONTINUA a
        acontecer no arranque — é preciso subscrever cedo para não perder
        LCP/TTFB, e a lib `web-vitals` é pequena. O que espera pelo SDK é só o
        ENVIO, que fica em fila.

  EDIT  src/Boot.jsx
        Sobe o Sentry em `requestIdleCallback` (timeout 5 s) quando a aplicação
        vai montar — nunca no gate, e deliberadamente depois de o chunk da app
        entrar em carregamento, para não competir pelo mesmo instante de CPU.

5 · TRADE-OFF ASSUMIDO (declarado, não escondido)
--------------------------------------------------------------------------------
  Se o utilizador ABANDONAR no gate LGPD sem aceitar, os eventos em fila NÃO
  chegam ao Sentry. Antes do MC82.3 chegariam, porque o SDK era inicializado no
  boot. Trocou-se cobertura de uma janela curta (o tempo do gate, com a app
  ainda não montada) por −256,5 KB no arranque.

  Mitigações que continuam de pé:
    · Os listeners globais [GUT-DEBUG] (error / unhandledrejection / CSP)
      registam tudo no console desde o primeiro instante — o diagnóstico manual
      com o operador não se perde.
    · A fila tem limite de 50 eventos, para não crescer sem controlo.

6 · ⚠️ PENDÊNCIA DE PRIVACIDADE QUE RESSURGIU (R4)
--------------------------------------------------------------------------------
  O `replayIntegration` continua com `maskAllText: false, blockAllMedia: false`
  e `replaysSessionSampleRate: 0.1` — ou seja, 10% das sessões gravam o texto do
  ecrã SEM MÁSCARA, num app com saldos, valores de lance e dados de carteira.

  Histórico: isto foi levantado como alerta R4 no MC82; o operador escolheu
  "manter, mas mascarado"; a alteração chegou a ser aplicada e foi REVERTIDA
  junto com o resto na correção de rota do MC82 — e nunca foi reaplicada.
  Movi a configuração para o sentryLazy.js INTACTA, de propósito: mudá-la de
  passagem seria uma alteração de comportamento fora do escopo deste MC.

  Correção de uma linha, quando o operador aprovar:

================================================================================
LIÇÃO QUE ESTE MC DEIXA
  Ao tornar telemetria lazy, separar SUBSCRIÇÃO de ENVIO. Os Core Web Vitals
  têm de ser subscritos cedo ou perdem-se; o SDK que os recebe pode chegar
  depois. Uma fila em memória entre os dois preserva a observabilidade sem
  pagar o custo de arranque — e o comportamento tem de ser validado por
  experimento (provocar um erro antes do init e confirmar o envio depois),
  não presumido a partir do código.
