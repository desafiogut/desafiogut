A CORREÇÃO ÓBVIA TEM UM PROBLEMA — E É PRECISO DECIDIR ANTES
================================================================================
O plano (S1.1) propõe estender a sessão otimista: guardar o tipo em cache e,
durante o restauro, redirecionar já para /corporativo.

Isso funciona para o REDIRECT. Mas há uma segunda guarda no caminho:

    CorporativoRoute (App.jsx:59)
        if (!ready) return null;
        if (!isConnected) { … return <Navigate to="/" /> }
        if (tipoCarregando) return null;
        if (tipoUsuario !== "corporativo") return <Navigate to="/" replace />;

Se eu redirecionar otimisticamente para /corporativo enquanto o tipo ainda não
foi confirmado, o utilizador aterra numa rota que:
   • devolve `null` enquanto `tipoCarregando` for true  → ECRÃ EM BRANCO,
     exatamente o defeito que o MC88.37 corrigiu;
   • e, se o palpite estiver errado, devolve <Navigate to="/"> → o utilizador
     é atirado de volta. Ida e volta em vez de uma ida errada.

Ou seja: corrigir só o `DashboardOuCorporativo` troca um problema por outro.
A correção tem de tratar os DOIS pontos com a MESMA fonte de verdade.

⚠️ E há uma diferença de natureza que eu não quero decidir sozinho.
No MC88.38 escrevi, e mantenho: "`pareceAutenticado` escolhe TEXTO, nunca
autorização". Aqui a otimização incide sobre uma GUARDA DE ROTA — que é
autorização. Renderizar o painel corporativo com base num palpite de cache é
diferente de escrever "Olá, Fulano" com base num palpite.

Mitigação real: o cache seria validado contra o endereço da sessão (a mesma
guarda síncrona do MC88.34), e os DADOS do painel vêm de chamadas autenticadas
que devolveriam 401/403 a quem não for lojista — o risco é mostrar a CASCA do
painel, não conteúdo alheio. Mas é uma decisão sua, não minha.


OPÇÕES
================================================================================
A) OTIMISTA NOS DOIS PONTOS (o que o plano pede)
   Guardar `tipoUsuario` no cache validado por endereço; usá-lo em
   `DashboardOuCorporativo` E em `CorporativoRoute` enquanto o real não chega.
   → lojista entra direto no painel, sem passar pelo comum.
   → risco: casca do painel visível a partir de um palpite; ida-e-volta se o
     palpite falhar (mitigável exigindo que a rota só bounce depois de
     `tipoCarregando` terminar).

B) NÃO ADIVINHAR, MAS TAMBÉM NÃO MENTIR
   Introduzir o terceiro estado a sério (`tipoUsuario` passa a poder ser
   `null` = desconhecido) e, enquanto for desconhecido, mostrar um ecrã neutro
   de transição em vez do Dashboard comum.
   → o lojista nunca vê o ecrã errado.
   → custo: TODOS os utilizadores (comuns incluídos) veem ~3-5 s de ecrã de
     transição no arranque — perde-se parte do que os MC88.37-40 ganharam.

C) OTIMISTA SÓ PARA QUEM JÁ ENTROU COMO LOJISTA
   Igual a (A), mas o palpite só é usado se a última sessão CONFIRMADA nesse
   mesmo endereço tiver sido corporativa. Um utilizador comum nunca vê o painel
   corporativo, nem por um instante, porque nunca terá esse cache.
   → mais conservador que (A), mesmo ganho para o lojista recorrente.
   → primeiro login corporativo de sempre continua a passar pelo comum.

CONTEXTO DE NEGÓCIO — PORQUE ISTO É PIOR DO QUE UM PISCAR
================================================================================
Lido em `docs/chatbot/regulamento.md` §3 e §4.1 e em
`docs/explanation/regras-de-negocio.md`:

O utilizador corporativo é um LOJISTA ANUNCIANTE, não um participante do leilão.
Compra uma cota de publicidade (Bronze R$ 2.640 → Diamante R$ 18.000), paga uma
Taxa de Adesão por PIX aprovada manualmente pelo Admin, e o que lhe interessa é:
banners na Vitrine e na app, cotas, analytics e a Wallet de vale-crédito.

As suas rotas são `/corporativo`, `/corporativo/cotas`, `/corporativo/banners`,
`/corporativo/analytics`, `/corporativo/carteira`.

O que ele vê durante os ~3-5 s de transição é o Dashboard COMUM: KPIs de leilão,
saldo de senhas, "Lances Únicos", "Total de Lances", "Edição Ativa", "Ir para o
Mercado de Lances", "Acesso Rápido" com Depositar PIX e Dar Lance.

Nada disso é o produto dele. Não é um flash de estilo — é a montra errada, e
para quem pagou entre R$ 2.640 e R$ 18.000 é a primeira coisa que vê ao abrir a
app. As rotas comuns estão inclusive na lista de `rotasProibidas` do próprio
efeito de redirect (AppContext:418) — o código já as considera impróprias para
ele; só chega tarde a essa conclusão.
