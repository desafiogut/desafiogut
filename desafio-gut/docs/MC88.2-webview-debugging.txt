2. PORQUE JÁ FUNCIONA SEM A FLAG NO CÓDIGO
################################################################################

Conteúdo integral de
`android/app/src/main/java/com/desafiogut/app/MainActivity.java`:

    package com.desafiogut.app;

    import com.getcapacitor.BridgeActivity;

    public class MainActivity extends BridgeActivity {}

É o `BridgeActivity` de fábrica do Capacitor, sem corpo. A depuração vem do
próprio Capacitor: o `Bridge` chama `WebView.setWebContentsDebuggingEnabled(true)`
quando a aplicação tem a flag `FLAG_DEBUGGABLE` — que é exatamente o que o
`dumpsys` mostra em §1.3. Num build debug isto é automático; não é preciso
escrever a linha.

  ► Acrescentar a chamada à mão seria redundante: ligar-se-ia uma coisa já ligada.

2.1 — ⚠️ ARMADILHA NO SCRIPT PROPOSTO (importa registar)
    O script do Segmento 1 procura inserir a flag com:
        $conteudo -replace "(onCreate.*?){", ...
    **Não existe `onCreate` neste ficheiro.** A substituição não encontraria nada
    e seria um no-op — mas o script imprime `✅ Flag adicionada` de forma
    incondicional, porque só verifica se o ficheiro foi *encontrado*, nunca se a

    fins de linha) sem qualquer ganho.

3. O QUE FOI ENTREGUE EM VEZ DA ALTERAÇÃO
################################################################################

`desafio-gut/scripts/webview-devtools.ps1` — script auxiliar de desenvolvimento
(ferramenta, não código da aplicação; o app não o carrega nem o empacota).

  O que faz, por ordem:
    1. confirma que há dispositivo autorizado;
    2. arranca o app se não estiver a correr (`-Reiniciar` força restart limpo);
    3. **descobre o PID** e monta o nome do socket — a peça que faltava;
    4. verifica que `webview_devtools_remote_<PID>` existe e, se não existir,
       lê as flags do pacote e diz explicitamente que o build não é depurável
       (aí sim seria caso para `assembleDebug`);
    5. monta o `adb forward`;
    6. confirma com `/json/list` e imprime título, url e `webSocketDebuggerUrl`.

  Uso:
      .\webview-devtools.ps1
      .\webview-devtools.ps1 -Reiniciar -Porta 9444

  Execução real de validação (2026-07-23):
      Dispositivo: fiem7xlvcufe855h
      PID: 13349
      DevTools ativo em http://localhost:9333
        titulo : DesafioGUT — O Menor Lance Único Ganha
        url    : https://localhost/
        ws     : ws://localhost:9333/devtools/page/4B7BFC160FC6932DD04C0CFAB09EE7ED

  Porque isto resolve de vez: o PID muda a cada arranque do app, logo o nome do
  socket muda também. Qualquer comando com PID escrito à mão fica obsoleto no
  próximo restart — e a falha volta a parecer "depuração desativada". O script
  elimina a classe inteira de erro.


################################################################################
4. SOBRE O chrome://inspect
################################################################################

O `chrome://inspect` usa o seu próprio mecanismo de descoberta e continua a ser
uma via válida — mas é a menos fiável das duas, e não é a que os MCs usam.

  Se não listar o app, verificar por esta ordem:
    1. em `chrome://inspect/#devices`, a caixa **"Discover USB devices"** tem de
       estar marcada;
    2. o dispositivo tem de estar autorizado (`adb devices` a mostrar `device`,
       não `unauthorized`);
    3. o app tem de estar em **primeiro plano** — um WebView em segundo plano
       pode ser descartado pelo sistema;
    4. conflito de versões de `adb`: o Chrome traz o seu próprio cliente e, se
       houver outro servidor adb de versão diferente a correr, a descoberta
       falha em silêncio. `adb kill-server` seguido de `adb devices` resolve.

  ► Para os MCs, a via canónica continua a ser o túnel + CDP por WebSocket nativo
    do Node, registada desde o MC82-BASELINE: o MCP chrome-devtools **não anexa a
    alvo remoto**, pelo que o `chrome://inspect` não substitui o túnel de qualquer
    forma.

################################################################################
6. LIÇÕES
################################################################################

L1 — `chrome_devtools_remote` é o socket do NAVEGADOR Chrome. Um WebView de
     aplicação expõe `webview_devtools_remote_<PID>`. Bater à porta errada produz
     exatamente o mesmo sintoma que "depuração desativada" — e leva a corrigir o
     que não está partido.

L2 — O PID entra no nome do socket, logo o alvo muda a cada arranque do app.
     Descobrir o PID em tempo de execução não é conveniência, é correção.

L3 — Antes de ativar uma flag, confirmar que ela não está já ativa por omissão do
     framework. O Capacitor liga o `setWebContentsDebuggingEnabled` sozinho em
     builds depuráveis; o `MainActivity` de fábrica é literalmente vazio.

L4 — Um passo de automação tem de validar o EFEITO, não a existência do alvo. O
     script proposto teria reportado `✅ Flag adicionada` sem ter alterado nada,
     porque só verificava se o ficheiro existia. Um sucesso falso é pior do que
     uma falha, porque encerra a investigação.

L5 — O relatório do MC anterior pode ser a prova que refuta o MC seguinte. O
     MC88.1 conversou com este WebView por CDP; isso, sozinho, já tornava a
     premissa do MC88.2 insustentável. Vale reler o que se acabou de fazer antes
     de aceitar um diagnóstico novo.
