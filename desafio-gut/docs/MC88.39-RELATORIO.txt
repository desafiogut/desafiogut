================================================================================
CAUSA RAIZ — AppContext.jsx:694-697
================================================================================
O `jaTeveEnderecoRef` foi introduzido pelo MC88.34 para distinguir duas
situações: "ainda não carregou" e "fez logout". É ligado a `true` no instante
em que o `address` chega (linha 590).

Mas no ramo de limpeza do saldo em R$ existem TRÊS situações, não duas:

    (a) arranque, sem endereço              → não limpar     ✅ tratado
    (b) arranque, com endereço sem token    → NÃO deve limpar ❌ NÃO tratado
    (c) logout real, endereço desapareceu   → limpar          ✅ tratado

    if (!address || !authToken) {
      if (jaTeveEnderecoRef.current) { …limpa… }   ← lê (b) como (c)
    }

No arranque o `address` chega ANTES do `authToken` (o token é obtido num pedido
próprio, umas centenas de ms depois). Nessa janela a condição era verdadeira
POR CAUSA DO TOKEN, mas o ref já estava `true` POR CAUSA DO ENDEREÇO. Falso
positivo de logout — e o saldo otimista era apagado.

PORQUE É QUE AS SENHAS NUNCA SOFRERAM DISTO: `refetchSaldo` guarda apenas
`if (!address)`. Assim que o endereço existe, o seu ramo de limpeza fica
inalcançável. O saldo em R$ tem uma pré-condição extra — o token — que a guarda
não cobria.

O "⏳" era CONSEQUÊNCIA, não uma fase independente: com o status posto a
"idle", a linha 700 (`prev === "ok" || prev === "stale" ? prev : "loading"`)
deixava de encontrar "stale" e promovia a "loading", que o Dashboard desenha
como relógio.

PORQUE O MC88.34 NÃO APANHOU: aplicou a mesma guarda aos DOIS refetch, com o
mesmo raciocínio, e validou o resultado pelo saldo de SENHAS — que era o alvo
declarado daquele MC. O relatório do MC88.34 diz "os dois refetch deixaram de
limpar o saldo quando address/authToken ainda não existem"; para o R$ isso só
ficou verdadeiro quanto ao `address`, não quanto ao `authToken`.

PENDÊNCIAS
================================================================================
 1. O saldo em R$ ainda só CONFIRMA aos ~5,8–6,3 s. Este MC eliminou o piscar,
    não a espera: o valor fresco depende do `authToken` e do pedido
    `/saldo-rs`, que só correm depois de o Privy validar a sessão pela rede
    (cadeia documentada no MC88.38-BASELINE-FRICCAO.txt). Enquanto isso, o
    utilizador vê o valor em cache com "(antigo)" — que é honesto, mas não é
    instantâneo.

 2. ⚠️ O sufixo "(antigo)" está exposto ao utilizador final. É jargão interno
    introduzido pelo MC88.34 (`statusSuffix`, Dashboard.jsx:73-79) para
    distinguir cache de confirmado. Visível na captura do MC88.38 como
    "R$ 0.00 (antigo)" e "12 (antigo)". Não é linguagem de produto. Fora de
    escopo deste MC (R1), mas é agora a fricção visual mais evidente que resta.

 3. Não foi auditado se o mesmo falso positivo de logout existe noutros pontos
    que dependam de `authToken` além do saldo (cotas, notificações). Só o
    caminho do R$ foi corrigido.
