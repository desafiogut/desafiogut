################################################################################
2. RLS (ROW LEVEL SECURITY)
################################################################################

2.1 ESTADO — TODAS AS TABELAS PROTEGIDAS ✅
Consulta a pg_class (relrowsecurity) sobre as 14 tabelas do schema public:
rowsecurity = true em 14/14. Nenhuma tabela sem RLS. Nenhuma view materializada
exposta (a migração que as cria não foi aplicada — o que, do ponto de vista de
segurança, é bom: MVs não respeitam RLS).

2.2 POLÍTICAS — 16 políticas, todas analisadas
  · 14 políticas "service_role total <tabela>" — FOR ALL TO service_role
    USING(true) WITH CHECK(true).
    VEREDITO: CORRETO. `USING (true)` só é perigoso quando concedido a
    public/anon/authenticated. Aqui o alvo é service_role, que já ignora RLS por
    natureza. O efeito real é DEFAULT-DENY para anon e authenticated.
  · "Leitura pública de produtos" — FOR SELECT TO public USING(true).
    VEREDITO: aceitável — catálogo é público por desenho, sem colunas sensíveis.
  · "Leitura pública de configurações" (config_remota) — FOR SELECT TO public
    USING(true). VEREDITO: aceitável — só feature flags.
  · fila_tarefas tem DUAS políticas idênticas ("service_role total fila" e
    "service_role_all") — redundância, não vulnerabilidade. Limpeza cosmética.

Nenhuma política usa auth.uid(). Isso NÃO é um defeito nesta arquitetura: o
projeto não usa Supabase Auth (a autenticação é Privy + JWT HS256 próprio nas
Netlify Functions). Como nenhum utilizador final chega ao Postgres autenticado,
o modelo correto é exatamente o adotado — negar tudo a anon/authenticated e
concentrar a autorização no backend. Recomendar auth.uid() aqui seria importar
um modelo que o projeto não usa.

  GET  /rest/v1/fila_tarefas           → HTTP 200  []   (RLS bloqueia)

2.4 ACHADO A-04 (P1) — reservar_tarefas é SECURITY DEFINER executável por anon
  Evidência: pg_proc.proacl = "=X/postgres" (EXECUTE para PUBLIC) + prosecdef=true;
  advisor 0028/0029 do Supabase; chamada anónima devolveu 200.
  Impacto: SECURITY DEFINER roda como owner e IGNORA o RLS de fila_tarefas.
  Qualquer pessoa na internet, com a chave anon (que é pública por desenho e está
  no bundle), lê o conteúdo da fila. Hoje a fila está vazia e inerte; quando for
  adotada, o payload conterá pedidoId, endereço de carteira e valores de crédito.
  Agravante: p_limit é controlado pelo chamador e não tem teto.
  Correção: REVOKE EXECUTE ON FUNCTION public.reservar_tarefas(integer) FROM
  PUBLIC, anon, authenticated; GRANT ... TO service_role. Fixar search_path.

2.5 ACHADO A-15 (P3) — search_path mutável
  update_fila_tarefas_updated_at e reservar_tarefas sem `SET search_path = ''`.
  Vetor de escalonamento clássico em funções SECURITY DEFINER.

2.6 RECOMENDAÇÕES RLS

3. VALIDAÇÃO DE DADOS (BACKEND)
################################################################################

3.1 PANORAMA
Não existe biblioteca de validação declarativa (zod/joi) — a validação é manual,
centralizada em _lib/validate.mjs. Apesar disso, a cobertura dos campos
CRÍTICOS é boa:
  · validarEndereco — regex /^0x[a-fA-F0-9]{40}$/ + normalização lowercase. ✅
  · validarQuantidadeFichas — Number.isInteger + faixa 1..100. ✅
  · calcularValorBRL — o valor é CALCULADO no servidor a partir da quantidade,
    nunca aceito do cliente. Este é o ponto mais importante de todo o fluxo
    financeiro e está correto. ✅
  · parseJsonBody — rejeita JSON inválido com erro tipado. ✅
  · sanitizeText(input, max) — trunca campos livres (nome/email/observação) em
    admin-aprovacao.mjs e cotas.mjs. ✅
  · validarCNPJ — algoritmo completo de dígitos verificadores. ✅
  · Allow-lists: analytics.mjs (eventos), cotas (categorias), edicoes (tipos),
    status de fila via CHECK constraint no Postgres. ✅
  · scrubSvg (banners) contra XSS em SVG. ✅

3.2 ACHADO A-10 (P2) — pagador.cpf aceito sem validação
  netlify/functions/iniciar-pagamento.mjs:68
    cpf: typeof p.cpf === "string" ? p.cpf.slice(0, 32) : undefined
  O CPF só é verificado como "é string" e truncado em 32 caracteres. Não há
  validação de comprimento (11), de dígitos verificadores, nem de formato. O
  campo segue para _lib/pix-provider/mercadopago.mjs, que faz normalizarDoc
  (só dígitos) e infere CPF/CNPJ pelo tamanho.
  Impacto: baixo-médio. Não há injeção (o valor vira JSON para a API do MP), mas
  um CPF malformado produz falha de pagamento tardia e opaca para o utilizador,
  e o e-mail (254 chars) também não é validado por regex antes de ser enviado.
  Nota positiva: o CPF NÃO é persistido em pedidos-meta — verificado em
  _lib/credito.mjs gravarMetaPedido (grava só endereco/qtd/valorBRL/paymentId).

3.3 ACHADO — ausência de teto de tamanho de corpo
  parseJsonBody faz req.text() sem limite. O limite efetivo é o do runtime da
  Netlify (~6 MB). Não é explorável para injeção, mas permite consumo de CPU
  gratuito em endpoints não autenticados (analytics é o mais exposto, mitigado
  por rate-limit de 30/min/IP).

3.4 FUNÇÕES COM VALIDAÇÃO ROBUSTA (referência de bom padrão)
  comprar-senhas.mjs · confirmar-pagamento.mjs · delete-account.mjs ·
  iniciar-pagamento.mjs (exceto 3.2) · edicoes.mjs · cotas.mjs (POST/DELETE).

3.5 RECOMENDAÇÕES
  R6. Adicionar validarCPF (dígitos verificadores) e validarEmail (regex) a

  R7. Introduzir zod progressivamente, começando pelos endpoints que movem

4.1 PROVA VIVA — OS ENDPOINTS FINANCEIROS ESTÃO PROTEGIDOS ✅

4.2 ACHADO A-01 (P0) — /cotas GET não recebeu o guard anti-IDOR
  Arquivo: netlify/functions/cotas.mjs, função handleGet.
  Enquanto POST e DELETE de cotas.mjs exigem ADMIN_TOKEN, o GET é INTEIRAMENTE
  ANÓNIMO. Quatro ramos vazam o cadastro de lojistas:

  (a) GET /cotas?cliente_id=0x<qualquer>
      → devolve o registo COMPLETO da cota daquele endereço (getCota).
      IDOR clássico: nenhuma verificação de propriedade.
  (b) GET /cotas?email=<qualquer e-mail>
      → devolve o registo COMPLETO (getCotaByEmail), incluindo tipo corporativo.
      Sem rate-limit neste ramo.
  (c) GET /cotas?cnpj=<qualquer CNPJ válido>
      → devolve { endereco, email, empresa }. Sem rate-limit neste ramo.
      CNPJs brasileiros são dado público → enumeração dirigida é trivial.
  (d) GET /cotas?categoria=ouro|prata|bronze|diamante
      → LISTA TODAS as cotas da categoria, com os registos completos.
      Divulgação em massa, sem sequer precisar de um identificador.

  Evidência viva (2026-07-22 03:3x UTC):
    GET /cotas?categoria=ouro   → 200 {"categoria":"ouro","total":0,"cotas":[]}
    GET /cotas?cliente_id=0x..1 → 404 cota_nao_encontrada
    GET /cotas?email=teste@...  → 404 email_nao_encontrado
    GET /cotas?cnpj=1122...     → 404 cnpj_nao_encontrado
  Os 200/404 provam que os ramos EXECUTAM sem autenticação. Vêm vazios apenas
  porque produção ainda lê Netlify Blobs. O Supabase JÁ TEM 7 cotas com cnpj e
  email reais: no dia do flip DATA_STORE_BACKEND=supabase, o ramo (d) passa a
  devolver, sem autenticação nenhuma, CNPJ + e-mail + carteira de todos os
  lojistas parceiros.
  Classificação P0 por isso: é uma violação de LGPD à espera de um deploy de
  configuração, não de um ataque sofisticado.

  Ramo adjacente, por desenho: ?acao=verificar-login&cnpj=&empresa= devolve o
  e-mail mediante CNPJ + nome da empresa (ambos dados públicos). Tem rate-limit
  de 10/min e mensagem genérica anti-enumeração — é o pré-passo do OTP, e o OTP
  é o gate real. Aceitável, mas deve ser o ÚNICO ramo público de cotas.

4.3 ACHADO A-05 (P1) — /debug-pedido aberto em produção
  Arquivo: netlify/functions/debug-pedido.mjs. O guard é opcional por desenho:
  "Sem DEBUG_TOKEN no env, o endpoint responde sem auth (modo dev)".
  Fail-open num endpoint de diagnóstico, em produção.
  Evidência viva: GET /debug-pedido?id=teste-auditoria-mc86 → HTTP 200, corpo
  incluindo "DEBUG_TOKEN_set": false — o próprio endpoint confirma que está
  desprotegido. Devolve também o mapa de configuração (PIX_PROVIDER,
  MP_ACCESS_TOKEN_set, signer_backend, biconomy_kms_set) e o endereço do
  contrato ativo.
  Impacto: com um pedidoId (UUIDv4, não adivinhável) obtém-se endereço de
  carteira, quantidade e valor do pedido de terceiro. O UUID limita a
  explorabilidade em massa, mas ele viaja em URLs, prints e suporte.

4.4 ACHADO A-09 (P2) — /admin-list GET público
  Evidência: GET /admin-list → 200
  {"admins":["0xda3a83…e84e"],"coordenacao":"0xda3a83…e84e"}
  Revela, sem autenticação, exatamente qual carteira controla a plataforma.
  Isso transforma um alvo difuso num alvo nomeado (phishing dirigido,
  engenharia social, vigilância on-chain da carteira).

4.5 ACHADO A-06 (P1) — a EOA comprometida continua a ser admin
  O endereço devolvido por /admin-list (0xDa3a83…e84E) é a EOA cuja chave
  privada foi exposta em conversa (registo MC59.11), e continua listada como
  admin E como coordenação na produção mainnet — enquanto o contrato mainnet
  ativo (0x0052…16cd) já usa outra coordenação (0xFea436…1E67).
  Mitigação existente (importante): auth-admin exige ADMIN_TOKEN **E** assinatura
  EIP-191 de um endereço da lista, com anti-replay de 5 min. Só a chave privada
  não basta. Mas a defesa passa a depender de um único segredo partilhado.
  Correção: remover a EOA queimada do Blob admin-list:admins e da variável de
  coordenação; rotacionar ADMIN_TOKEN.

4.6 ACHADO A-02 (P0) — chave privada bruta no ambiente mainnet

  O problema é a porta de entrada:
    if (!secret) { ... return { ok: true, enforced: false } }
  Sem MP_WEBHOOK_SECRET, a validação é PULADA e o webhook aceita qualquer
  requisição. O interruptor MP_WEBHOOK_ENFORCE existe (MC59.2) mas é opt-in.
  Indício de que continua em fail-open: o código dispara captureSecurityAlert
  ("webhook_mp_fail_open") precisamente para sinalizar ao operador que o segredo
  falta — e a memória do projeto regista essa pendência desde o MC39.17.
  Mitigações que reduzem (mas não anulam) o risco: o status e o valor são
  RE-CONSULTADOS na API do MP com o paymentId, e o crédito é idempotente por
  pedidoId. Um atacante não inventa um pagamento; consegue, isso sim, forçar
  processamento arbitrário e enumerar paymentIds válidos.
  Correção: definir MP_WEBHOOK_SECRET (painel do MP) e MP_WEBHOOK_ENFORCE=true.
  Ação do OPERADOR — o agente não manuseia segredos (R5).

6.3 ACHADO A-07 (P2) — sem proteção anti-replay
  O `ts` do header entra no manifest assinado, mas o seu FRESCOR nunca é
  verificado. Não há a janela de 5 minutos que o briefing pede (secção 5.4), nem
  registo de x-request-id já visto. Mesmo com o segredo configurado, uma
  notificação legítima capturada pode ser reenviada indefinidamente.
  Impacto real limitado pela idempotência por pedidoId, mas é gasto de quota da
  API do MP e ruído de auditoria.
  Correção: rejeitar se |agora − ts| > 300 s; opcionalmente memorizar
  x-request-id por 24 h em Blob/Redis.

6.4 ACHADO A-08 (P2) — a assinatura cobre a query, o processamento usa o body
  A assinatura é calculada sobre o `data.id` da QUERY STRING:
    validarAssinaturaMp(req, new URL(req.url).searchParams.get("data.id") || ...)
  Mas extrairPaymentId dá PRECEDÊNCIA ao body:
    let paymentId = bodyId || qpId;   (bodyId = body.data.id || body.resource || body.id)
  Consequência: uma requisição assinada para o pagamento X, com o corpo alterado
  para o pagamento Y, passa na verificação e processa Y. A assinatura não cobre
  o valor efetivamente usado — falha de cobertura, não de criptografia.
  Impacto contido (o crédito segue o external_reference devolvido pelo MP, logo
  vai para o dono legítimo), mas invalida a garantia de integridade que a
  assinatura deveria dar.
  Correção: assinar/verificar o identificador que será REALMENTE processado, ou
  exigir que query e body coincidam.

6.5 PENDÊNCIA — SendGrid Event Webhook
  Se algum dia forem ativados webhooks de bounce/entrega no painel SendGrid
  (risco N1 já registado no projeto), não existe hoje endpoint que valide a
  assinatura ECDSA X-Twilio-Email-Event-Webhook-Signature. Não criar o receptor
  sem a validação.
