    t=4509 ms   scrollH= 828   NENHUM bloco     ← página em branco

Só o rodapé e a barra de navegação. **O CLS de 0,373 era o sintoma de um ecrã

CAUSA RAIZ — App.jsx:80
================================================================================
    function DashboardOuCorporativo() {
      const { tipoUsuario, tipoCarregando, isConnected } = useAppContext();
      if (isConnected && tipoCarregando) return null;        // ← aqui
      ...
    }

Cronologia:
  1. Arranque: o Privy ainda não restaurou → `isConnected` é FALSE. A guarda
     não dispara e o Dashboard pinta normalmente (~1,7 s).
  2. ~4,3 s: o Privy conclui → `isConnected` passa a TRUE. No MESMO instante o
     `authToken` passa a existir e `AppContext.jsx:350` liga
     `setTipoCarregando(true)` para ir buscar as cotas.
  3. As duas condições ficam verdadeiras ao mesmo tempo → `return null` → o
     `<Outlet />` esvazia-se. O `<Layout>` fica, e é por isso que o rodapé
     colapsa para altura 0 em vez de desaparecer do DOM.
  4. ~5,5 s: as cotas respondem, o Dashboard remonta. Segunda deslocação.

NÃO era o `<Suspense>`: o seu fallback é o `RouteFallback` ("⏳ Carregando…") e
esse texto nunca aparece em nenhuma amostra; além disso a fronteira teria
substituído o Layout inteiro, e o rodapé manteve-se montado.

A GUARDA NÃO PROTEGIA NADA. O comentário em `AppContext.jsx:252` declara a
intenção — *"tipoCarregando evita redirect prematuro"*. Evitar um REDIRECT, não
apagar a página. E o Dashboard comum JÁ é mostrado durante os ~4,3 s anteriores,
enquanto `isConnected` é false: apagá-lo só depois disso não impede que um
utilizador corporativo veja o ecrã comum. Só acrescenta o branco.

    function DashboardOuCorporativo() {
      const { tipoUsuario, tipoCarregando } = useAppContext();
      if (tipoUsuario === "corporativo" && !tipoCarregando) {

Deixa de devolver `null` e adia apenas o REDIRECT — que era a intenção
declarada. Durante a deteção mostra-se o Dashboard, exatamente como já
acontecia nos 4,3 s anteriores.

O caso corporativo mantém DUAS camadas: o `<Navigate>` local (agora com
`!tipoCarregando` explícito) e `AppContext.jsx:409-424`, que já esperava por
`tipoCarregando` antes de navegar.

⚠️ BUG NOVO, REPORTADO PELO OPERADOR DURANTE ESTE MC — DIAGNOSTICADO, NÃO CORRIGIDO
================================================================================
O operador notou que "ele entra numa página antes". Está nos meus próprios
dados do S0 e eu tinha passado ao lado. Medido no APK JÁ corrigido:

    t=1244 ms   "Bem-vindo ao DesafioGUT! | Faça login para participar…"
                              …e ao lado:  "R$ 0.00 (antigo) | 12 (antigo)"
    t=2842 ms   "Olá, Novo Pernambucano! | Acompanhe seus dados…"

Durante **1,6 segundos** um utilizador JÁ AUTENTICADO vê um ecrã a mandá-lo
fazer login — com o saldo dele próprio pintado ao lado. É autocontraditório.

CAUSA (mesma família da que este MC corrigiu, mas ponto diferente do código):
  `AppContext.jsx:433` → `const isConnected = authenticated && Boolean(address);`
  `Dashboard.jsx:176/186` usa `isConnected` como BINÁRIO: ou está ligado, ou
  manda fazer login. Não existe o terceiro estado "ainda a restaurar".
  Durante o restauro do Privy, `ready` é false e `authenticated` é false, logo
  cai-se no ramo "faça login".

O `ready` do Privy JÁ está exposto pelo AppContext (linha 1016), portanto o
terceiro estado é distinguível sem infraestrutura nova.

CORREÇÃO SUGERIDA (coerente com o que a app já faz): o MC88.34 já pinta o saldo
otimista a partir do cache validado contra a sessão em disco. O cabeçalho devia
seguir a MESMA política — enquanto `!ready`, não afirmar "faça login". O helper
de deteção de sessão por existência de chaves já existe desde o MC88.36 S4
(`PrivyRoot.jsx`, sem ler conteúdo — R5).

NÃO O APLIQUEI: está fora do escopo declarado do MC88.37 (R1), que é o CLS.
Fica como MC88.38 sugerido, ou digo-me que o faça já.
