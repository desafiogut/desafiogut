• É DDL na base de PRODUÇÃO (Supabase) — ação outward-facing e difícil de reverter.

  projeto, o OPERADOR manuseia segredos; o agente não os puxa/usa.
• O cabeçalho da própria migração diz: "Execução pelo OPERADOR (R12). NÃO aplicada
  por código."

  o token/senha do projeto — que é do operador.
(Sem acesso ao banco, o agente também não pode fazer a verificação pré/pós — as
 queries de validação estão no runbook para o operador executar.)

2. CORREÇÃO DO PLANO — a tabela é `fila_tarefas`, NÃO `fila_credito`
--------------------------------------------------------------------------------
O plano propôs criar `public.fila_credito` (job_id/quantidade/tx_hash/...). ISSO
ESTÁ ERRADO para este codebase:
  • grep por "fila_credito" em todo o repo → NADA (a tabela não é referenciada).
  • O worker (worker-credito.mjs) e a fila (_lib/fila.mjs) usam a tabela GENÉRICA
    `fila_tarefas` (colunas tipo/payload jsonb/status/tentativas/…) + a RPC
    `reservar_tarefas` (claim atômico FOR UPDATE SKIP LOCKED).
  • Criar `fila_credito` produziria uma tabela ÓRFÃ (nada a usa) e NÃO criaria o
    que o worker precisa → o async continuaria quebrado.

A MIGRAÇÃO CORRETA JÁ EXISTE NO REPO (não precisa reconstruir):
  desafio-gut/frontend/supabase/migrations/20260629_fila_tarefas.sql
Ela cria: tabela `fila_tarefas`, índice parcial `idx_fila_elegiveis`, RLS
(service_role), e a função `reservar_tarefas(p_limite INT)`.
