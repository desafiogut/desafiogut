## 5. Frontend implementado

### 5.1 O defeito real (medido, não suposto)

`grep` provou que a regra não existia em lado nenhum. `escolherEspecial`
(`_estilo-especial.js`) terminava com:

```js
return lista.find((e) => estadoEspecial(e, agora) !== ENCERRADA) ?? lista.at(-1);
```

=> quando todas as especiais já acabaram, devolvia a **última para sempre**. O Dashboard
ficava permanentemente preso ao sorteio do dia 04/10, meses depois.

### 5.2 O que foi feito

```js
export const RETENCAO_APOS_FIM_MS = 24 * 60 * 60 * 1000;      // R18: "24h após o fim"
export function dentroDaRetencao(edicao, agoraMs) {
  const fim = msDe(edicao?.termino_em);
  if (fim == null || !Number.isFinite(agoraMs)) return false;
  return agoraMs <= fim + RETENCAO_APOS_FIM_MS;
}
```
+ filtro `... && dentroDaRetencao(e, agoraMs)` em `escolherEspecial`.

A retenção é sobre o **fim** (antes de abrir também se mostra — o fim está no futuro).
Sem `termino_em` legível não se mostra: não se inventa janela.

## 9. Recomendações para o MC94.4 (inspecção geral + faxina)

1. **⚠️ [PRIORIDADE 1] Id com sufixo em minúsculas escapa a TODAS as guardas.**
   `^ESPECIAL-[A-Z0-9]+$` não apanha `ESPECIAL-airfryer`. O validador independente mediu
   o alcance real, e é maior do que uma gralha de admin: **`EDICAO_ID_RE` em
   `edicoes-core.mjs` usa o MESMO padrão, e em `listarEdicoes` as chaves inválidas são
   silenciosamente ignoradas (`continue`)**. Com um id desses, acontece tudo ao mesmo tempo:
   a guarda não dispara (**a especial pontuaria o torneio**), o cron nunca a encerra nem
   consolida, a retenção de 24 h não se aplica, e a edição **desaparece do dashboard**.
   É fail-closed quanto a "não pontua" e **fail-silent quanto ao auto-fecho** — o pior dos
   dois modos, porque ninguém é avisado. Mitigação hoje: os ids nascem de
   `scripts/mc941-seed-edicao-especial.mjs` (`CHAVE = "ESPECIAL-AIRFRYER"`, constante) e a
   UI usa o mesmo regex. Correcção sugerida: normalizar o id para maiúsculas no ponto de
   entrada (`.toUpperCase()`) **e** logar em vez de ignorar as chaves inválidas em
   `listarEdicoes`; mais um teste por cada efeito. Não foi feito agora porque o regex é
   partilhado e a mudança não é comprovadamente necessária para este MC (R1).
2. **Teste flaky sob paralelismo**: `src/hooks/__tests__/hooks-torneio.test.mjs` falha 1
   de 28 sob carga ("um pedido novo limpa o erro do anterior": `demora: 20 ms` contra
   `carregando === true`). Isolado passa sempre; em série 344/344. Pré-existente, não
   regressão. Corrigir a asserção (por evento, não por temporização) ou subir o `demora`.
3. **`git add -A` é uma armadilha** neste repo (apanha os untracked de `docs/`). Usar
   caminhos explícitos.
4. **`npm install` do build suja o `package-lock.json`.** Verificar `git status` depois de

5. **[MÉDIA] Teste frágil a CRLF e repo sem `.gitattributes`.** `mc93e-ci-config.test.mjs`

6. **[BAIXA] O prefixo de log mudou** de `[consolidar-lances]` para `[consolidacao]` na

7. **[BAIXA] `TIMEOUT_MINER_MS` passou de constante interna a `export`** — mudança de

8. **[L-4 herdado] Durabilidade do marcador do cron.** `getStore({consistency:"strong"})`

## 10. Lições aprendidas

1. **O briefing não é a fonte da verdade; o código é.** O MC94.3.1 pedia para subir o
   `EdicaoBanner` a 96 px dentro do slot — mas o slot é um **teste commitado** que diz o
   contrário. Ler o teste antes de escrever código evitou reescrever um requisito de que
   não se sabia a razão.
2. **Contagens do briefing ≠ contagens reais.** "34/34" saía 51 porque o glob
   `mc93b-*.test.mjs` apanha dois ficheiros que a suíte anterior já contava, e
   `mc33-load.test.mjs` **não existe** (o ficheiro é `.mjs`). 0 falhas é o que importa.
3. **Mutação antes de confiar num teste.** Os 4 mutantes foram mortos por testes com nome.
4. **Duvidar de si mesmo antes de acusar o código.** Por pouco não se reportou um falso
   "buraco de cobertura" no caminho `202`: o grep inicial tinha lido o ficheiro errado.
   Um `grep` a mais custa segundos; um falso positivo custa credibilidade.
5. **Provar entrega por bytes, não por mensagem.** O CLI diz "Deploy is live!"; isso não
   prova que o **código novo** está servido. O `sha256` local vs servido, mais o código
   minificado legível no bundle, provam-no.
6. **O working tree de outro agente é sagrado.** Sem stash/reset/checkout. Medir, validar,
   continuar.
7. **Teste flaky ≠ regressão.** Isolar antes de acusar (28/28 isolado vs 27/28 paralelo).
8. **Higiene de efeitos colaterais.** Um build pode alterar ficheiros rastreados
   (`package-lock.json`). Verificar `git status` e reverter o que não é do escopo.
9. **Não ler um `grep` parcial como se fosse o resumo.** Errei aqui: escrevi no log do SEG6
   "backend 606 pass / fail 0" a partir de um grep truncado, quando o número real era
   `613 testes / 606 pass / 1 fail` (um teste frágil a CRLF, provado não-regressão pelo
   validador). Corrigido no mesmo log, com a correcção à vista. **A medição tem de vir do
   resumo da ferramenta, não de uma linha filtrada** — é a mesma regra que me fez voltar a
   medir quando quase acusei um falso buraco de cobertura, aplicada a mim próprio.
10. **Questionar a conclusão do validador também.** Ele concluiu — correctamente — que a
   retenção de 24 h não estava provada em produção, mas o âmbito dele era o commit
   `47cdc65` (pré-adendo) e o orçamento de iterações. Não é contradição: é um limite
   temporal e de ferramenta. Fechou-se depois, no re-deploy, com prova por bytes e por DOM.

## 11. Como cheguei aqui — o raciocínio, passo a passo

Esta secção existe porque foi pedida: o **método**, não o resultado.

### 11.1 A ordem que seguí, e porquê

**Medir o working tree antes de tocar em nada.** `git status --porcelain`, `git log -3`,
`git stash list`. Não por ritual: se houvesse uma stash ou um reset prévio, qualquer
trabalho a seguir construiria sobre ruína. Custou 1 comando e fechou a maior variável.

**Ler o código do Opus antes de o julgar.** Ler os 4 ficheiros inteiros (não os trechos que
o briefing descrevia) foi o que permitiu ver que a guarda estava **acima** do
`calcularPontosRodada` — ou seja, que o "zero escritas" era literal e não retórico. Se
tivesse confiado na descrição, teria "confirmado" sem saber.

**Provar a compatibilidade por diff, não por relato.** O Opus relatava 34/34 verdes. O
briefing pedia para confirmar que a extracção não mudara nada. Em vez de aceitar "os testes
passam", comparei o ficheiro antigo com o novo, linha a linha (`diff`), e classifiquei cada
diferença: forma (imports, helpers, prefixos de log) vs fundo (nenhuma). Foi isso que
permitiu afirmar byte-compatibilidade em vez de a supor.

**Correr as suítes por mim, por segmento, e depois globalmente.** Os números do briefing
não bateram (56, 34, 589/590). Não os "corrigi" para baterem: voltei a medir e expliquei a
divergência (globs, ficheiros que não existem). **Uma contagem que não bate é informação,
não ruído.**

**Mutar antes de confiar.** Antes de escrever "os testes cobrem a guarda", quebrei a guarda
e vi os testes ficarem vermelhos com nome. O passo 4.3 foi o mais instrutivo: quase
reportei um buraco de cobertura no caminho `202` porque o meu primeiro `grep` tinha lido o
ficheiro errado. **Voltei a medir antes de acusar** — e o buraco não existia.

**Ir ao frontend com os olhos abertos, e recuar com critério.** Era aqui que estava o
trabalho "por fazer". O caminho fácil era implementar o que o briefing pedia. Antes disso,
procurei o **teste** que descreve o ecrã — e encontrei, em `Dashboard.test.mjs:85`, um
teste que **exige o contrário** do que o briefing pedia. Nesse momento a decisão deixou de
ser técnica e passou a ser de engenharia: reescrever um requisito sem saber porquê, ou
fechar o que é seguro e documentar o resto. Escolhi o segundo — e implementei, em vez de
adiar, a **única** parte inequívoca (a retenção de 24 h), que corrigia um **defeito real**
que ninguém tinha notado: a especial encerrada ficava no Dashboard para sempre. Encontrei-o
por `grep`, não por intuição.

**Escrever o teste antes do código, mesmo com pressa.** O teste novo arrancou com um
`SyntaxError` do import — um vermelho feio, mas um vermelho **verdadeiro**. Só depois
implementei. O mesmo para a mutação: antes de declarar "o teste protege isto", quebrei o
código e vi qual teste morria.

**Provar a entrega no artefacto, não na mensagem.** O `netlify` disse "Deploy is live!".
Isso diz que o deploy correu, não que o meu código lá está. Comparei `sha256` do bundle
local com o servido (iguais) e depois **li o meu próprio código minificado dentro do
bundle de produção** — `Gt=1440*60*1e3` e a função `$t` replicada a partir do que escrevi.
Foi a única prova que aceitei.

**Desconfiar de efeitos colaterais que eu próprio causei.** O validador apanhou o
`package-lock.json` a mudar durante a validação. Não era sabotagem nem regressão: era o
`npm install` do **meu** build. Revertido, com o raciocínio escrito. **Um bom detetive
inclui-se na lista de suspeitos.**

### 11.2 Os 3 momentos em que mudar de rumo foi a decisão certa

1. **Quando os números não bateram** — em vez de forçar o alinhamento com o briefing,
   tratei a divergência como um achado a explicar.
2. **Quando o "buraco de cobertura" apareceu** — em vez de reportar, voltei a medir e
   descobri que o erro era meu.
3. **Quando o briefing contradisse o código** — em vez de obedecer, medi, percebi, e
   documentei a contradição com o HARD GATE 8 em vez de a resolver por conta própria.

### 11.3 O que faria diferente

- Ter perguntado ao operador, **antes** de arrancar, quais eram as decisões D do briefing
  do MC94.3 (a janela em que a especial substitui a R-1). Com elas, o MC94.3.2 teria sido
  feito agora. Sem elas, a paragem foi a decisão correcta.
- Ter verificado `git status` **imediatamente** após o build, em vez de deixar o validador

### Lição de método

O HARD GATE 8 do briefing salvou este MC de um erro: sem ele, teria reescrito um teste
