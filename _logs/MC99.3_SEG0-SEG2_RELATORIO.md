## SEG1 — DIAGNÓSTICO (causa-raiz, não sintoma)

### A timeline medida

```
314 ms  → router.js + css + index.js + react.js  (em paralelo)
733 ms  → react.js termina           ← first-paint = 712 ms
849 ms  → SÓ AGORA começam as fontes, o mascote e a imagem de fundo
966 ms  → fundo-loop-v3-desktop.webm (345 KB) começa
1291 ms → último recurso termina     ← FCP = 1512 ms
```

**O browser não sabe que estes recursos existem até o React correr.** O `index.html` tinha
**ZERO preloads** (medido: `grep -c 'rel="preload"' index.html` → 0). O `react.js` acaba aos
733 ms e só aos **849 ms** é que começam 6 pedidos críticos — uma janela morta de ~120 ms que,
somada ao tempo de cada recurso (225–374 ms), empurra o FCP para os 1512 ms.

**É a categoria CRÍTICA nº1 das regras da Vercel: *Eliminating Waterfalls*.** A causa não é
"o bundle é grande" (o privy nem carrega) nem "o CSS é lento" (54 KB). É que **nada é
descoberto cedo**.

## SEG2 — OTIMIZAÇÃO 1 (a única)

**`index.html`:** 5 preloads do que está **acima da dobra**, mais nada:

- `inter-400` (corpo) + `inter-900` (título), ambos `as="font" type="font/woff2"` **`crossorigin`**
  (sem `crossorigin` uma fonte é descarregada **duas vezes** — é por isso que este atributo é
  guardado por teste);
- o mascote do gate (`guto-bemvindo.png`, 15 KB);
- o fundo **na variante do ecrã** (`media="(min-width: 768px)"` / `(max-width: 767.98px)"` — o
  breakpoint real do app, lido de `useIsMobile.js` e não inventado).

**O vídeo de 345 KB NÃO é pré-carregado** — decisão deliberada e guardada por teste: é
decorativo e competiria com o que pinta primeiro.

**Escopo:** 1 ficheiro de código (`index.html`), 5 linhas. Nenhuma dependência, nenhum
componente reescrito, nenhuma lógica tocada. **Ponytail: o diff mais curto que funciona.**
