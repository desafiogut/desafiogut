V3 — MIGRAÇÃO SQL ................................ APROVADO COM RESSALVAS
================================================================================
IDEMPOTÊNCIA: sim. `CREATE TABLE/INDEX IF NOT EXISTS`, `DROP POLICY IF EXISTS`
antes de `CREATE POLICY`, `ALTER TABLE … ENABLE RLS` idempotente, tudo em
BEGIN/COMMIT. Ressalva habitual e não mitigada: se uma das tabelas já existir
com outra forma, o `IF NOT EXISTS` salta em silêncio e nenhuma coluna ou
constraint é acrescentada.

`posicao: 0` INICIAL: **PERMITIDO**. `posicao INT NOT NULL DEFAULT 0` +
`CHECK (posicao >= 0)`. Coerente com `pontuacao-store.mjs:117`. PASSOU.

ENDEREÇOS EM MINÚSCULAS: **SIM**, o CHECK é satisfeito.
`pontuacao-utils.mjs:normalizarEndereco` e `pontuacao-store.mjs:normalizar`
baixam ambos. RESSALVA: um endereço que seja string não-vazia mas não 40-hex
(ex.: `"0xa"` — literalmente o valor usado no mock de `getLances` do teste de
endpoints) passa `lanceValido` e depois viola
`pontuacoes_endereco_check`; e, por V1.f, é descartado **em silêncio**. A
mutação M7 (deixar de baixar para minúsculas) sobrevive à suíte.

`rankings_ciclo_liquidacao_check` — não bloqueia NADA do que o código escreve
hoje (o store preserva sempre `liquidado_em` e só soma a `senhas_a_creditar`).
⚠️ MAS bloqueia a liquidação óbvia: `UPDATE … SET liquidado_em = now(),
senhas_a_creditar = 0` viola a constraint (23514). O modelo implícito é «a
dívida fica registada para sempre e só se marca a data», e o índice parcial
`idx_rankings_ciclo_por_liquidar` assume o mesmo. Isto tem de estar escrito
ANTES de alguém escrever o handler, ou o handler nasce a falhar.

REVOKE/GRANT — **INSUFICIENTE face ao precedente do próprio projeto.**
O padrão nas duas migrações anteriores é REVOKE **emparelhado com** GRANT:
  20260722_mc87:52-53  REVOKE … FROM anon, authenticated;
                       GRANT EXECUTE … TO service_role;
  20260802_mc8943:71-72 REVOKE … FROM PUBLIC, anon, authenticated;
                        GRANT EXECUTE … TO service_role;
Esta migração faz o REVOKE e **omite o GRANT a `service_role`**. Funciona *se*
os default privileges do Supabase para o role que executa concederem ALL a
service_role (verdade quando corre como `postgres`). Se não for o caso, toda a
escrita falha com 42501 — e, por V1.f, **em absoluto silêncio, com resposta
200 OK**. Correcção de uma linha:
    GRANT ALL ON public.pontuacoes, public.rankings_ciclo TO service_role;
O que NÃO falta, verificado: não há sequências (`gen_random_uuid`, com
precedente em 4 migrações anteriores — `20260620_schema_definitivo.sql:14`,
`20260629_fila_tarefas.sql:10`, …), e `USAGE` no schema `public` é default.
A política `FOR ALL TO service_role` é redundante (service_role tem BYPASSRLS)
mas é o padrão do projeto e é inócua.

Menor: `idx_rankings_ciclo_por_liquidar` indexa `(liquidado_em)` sob o predicado
`liquidado_em IS NULL` — a coluna-chave é sempre NULL dentro do índice; só o
predicado serve. `(ciclo_id, endereco)` seria a chave útil.
