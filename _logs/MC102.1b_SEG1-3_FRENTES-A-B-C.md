## Frente B — `webhook-frenet.mjs` (novo)
Sequência do handler:
1. Método ≠ POST → 405.
2. **Sem `FRENET_WEBHOOK_TOKEN` → 503 (fail-closed).**
3. Header **`x-frenet-token`** ≠ segredo → 401. A comparação é `timingSafeEqual` com o mesmo comprimento.
4. JSON inválido ou sem `TrackingNumber` → 400.
5. Código de nenhum pedido → **200 `ignorado`**, para a Frenet não reenviar para sempre.
6. Sem tipos mapeados → 200 `ignorado`.
7. Grava via `registrarEventosRastreio`. Um reenvio dá **200 `duplicado:true`, com o blob byte a byte igual**. Um conflito CAS ou o store indisponível dão **503** (para a Frenet voltar a tentar).

- **`FRENET_WEBHOOK_TOKEN` é um segredo NOVO** (não é o `FRENET_TOKEN` da API) e **NÃO foi criado pelo executor**: é uma credencial nova, que o enunciado não autoriza. Até o operador a definir, o webhook responde 503 a tudo.
- **Testes:** `_tests/webhook-frenet.test.mjs` (17). Handler e lib **reais**, Blobs em duplo do MC102.0. Cobrem:
  - fail-closed; token errado / ausente / mais longo / em maiúsculas; GET;
  - evento novo; **reenvio 3× byte-idêntico**; mesma hora com outro tipo; sequência 0→1→5→9 até a timeline estar toda feita;
  - tracking desconhecido; caixa; tipo não mapeado; corpo inválido;
  - **CAS em conflito → 503**; **2 webhooks em paralelo → os 2 gravados**;
  - LGPD; >50; código diferente; sem pedido.
- **Mutação B+C: 17/17 RED:**
  - fail-open · sem token · prefixo · sem caixa · aceita GET · 404 em desconhecido · conflito=200 · JSON rebenta;
  - sem dedup · dedup só por código · duplicado grava · evento inteiro · sem limite · 50 mais antigos · sem conferir o código · casamento sensível à caixa;
  - **escrever sem `atualizarPedido` (setJSON directo)**: morto pelo teste de paralelismo.
