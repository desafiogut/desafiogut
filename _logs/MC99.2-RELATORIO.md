## 3. ⚠️ A medição corrigiu o enunciado em 3 pontos

### 3.1 «O app cria múltiplos clientes Supabase» → **FALSO como estava escrito**

Existe **um único** sítio a criar cliente (`supabaseClient.js:29`) e já era singleton *lazy*.
A causa real: **o singleton guardava o VALOR, dentro de uma função `async`.**

```
if (_client) return _client;              // ← dois chamadores passam os DOIS
const { createClient } = await import(…)  // ← a janela está aqui
_client = createClient(…)
```
Dois effectos de montagem chamam-no no mesmo tick (`useRealtimeConfig.ligar()` e
`useRecursosApp.carregarRecursos()`) → ambos passam o `if` antes de qualquer escrita → **dois
clientes** → «Multiple GoTrueClient instances». **Não eram dois `createClient`: era UM, com
uma janela.**

**Correcção:** memorizar a **promessa** (`_promessa`), não o valor. A 2.ª chamada recebe a
mesma promessa em voo. Detalhe que importa: o `.catch` **solta** a promessa para permitir nova
tentativa — um singleton que morre no primeiro erro de rede é pior que o problema original.

### 3.2 «O hook `useRecursosApp` subscreve mal» → **FICHEIRO ERRADO**

`useRecursosApp.js` **não subscreve nada** — faz um `select` pontual e cai em fallback para a
Netlify Function. Quem subscreve é **`useRealtimeConfig.js`**.

### 3.3 «O `.on()` está depois do `.subscribe()`» → **A ORDEM JÁ ESTAVA CERTA**

`L58-74`: `.channel().on().subscribe()` — correcta. **Corrigir a ordem não teria mudado nada.**

A causa real é uma **corrida temporal**: `sb.removeChannel()` é assíncrono e era chamado
**sem `await`**. Como o `supabase-js` **deduplica canais por topic**, o reconnect pedia
`sb.channel("config_remota:X")` antes de a remoção terminar, **recebia o canal antigo ainda
subscrito**, e o `.on()` seguinte rebentava exactamente com o erro de produção.

**Correcção:** `await sb?.removeChannel(c)` (+ `canal = null` **antes** do await, para que
duas limpezas concorrentes não removam o mesmo canal duas vezes).

### 5.2 Consola — MEDIDA NO CARREGAMENTO, COM CONTROLO POSITIVO


**O controlo positivo é o que transforma «consola vazia» em evidência.** Sem ele, «0 erros» e
«captador cego» são indistinguíveis — foi o erro que a série já pagou («saída vazia do
reporter = não medi»). Com ele: **não há os 3 erros no carregamento da app**, e o captador
vê o que se passa.

### 5.3 ⚠️ O QUE NÃO FOI MEDIDO — e porquê (declarado, não contornado)

Os 3 erros só podem aparecer **depois do gate LGPD**, porque é aí que os hooks que criam o
cliente e subscrevem correm. Medido: no ecrã do gate, `performance.getEntriesByType("resource")`
mostra **uma única origem** — o próprio app. **Nenhum pedido ao Supabase foi sequer tentado
antes do gate.**

**Não aceitei o gate.** Esse clique é um **consentimento legal** em nome do operador
(declaração de maioridade, tratamento de dados LGPD/GDPR e **cessão de imagem**, Art. 29) —
não é meu para dar. O operador aceita-o em 5 segundos e relê a consola; eu não o faço por ele.

**Substituto usado:** o CSP por header (o pedido que estava bloqueado passa agora) + a suíte
verde + o artefacto implantado a partir de `2502ccb`. Fica registado como **não medido**: a
consola **pós-gate**.

## 8. Lições

1. **A medição corrigiu o enunciado em 3 de 3 pontos técnicos** (onde estava o cliente, qual
   o hook, e a ordem das chamadas). Se eu tivesse «cumprido o pedido» — juntado clientes

2. **Um singleton que guarda o valor dentro de `async` não é um singleton.** É a definição de
   «instância única» que falha, não a contagem de chamadas.
3. **Vaciar a consola não é medir a consola.** O controlo positivo (injectar um erro e vê-lo
   aparecer) é o que separa «0 erros» de «captador cego».
4. **Há coisas que não se mede por quem não pode consentir.** O gate LGPD é um acto legal com
   nome do operador; a resposta certa é declarar o limite, não contorná-lo.
