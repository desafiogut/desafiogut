═══ A CAUSA RAIZ VERDADEIRA ═══
  A evidência diz duas coisas decisivas: `login completo` e `temAddress: true` +
  `temAuthToken: true`. **O login CONCLUIU.** O que falta é a app SAIR de /redirect.

  $ grep -n 'redirect' src/App.jsx | grep -i "path=\|Route"     -> VAZIO
  $ grep -n 'path="\*"' src/App.jsx                              -> VAZIO (nem catch-all)
  /redirect só existia como `customOAuthRedirectUrl` no PrivyRoot.jsx:217 — pensado para o
  deep link NATIVO (Capacitor, App Link HTTPS). Em web, o efeito que trata o deep link
  começa com `if (typeof window === "undefined" || !window.Capacitor) return;` — é NO-OP.
  Resultado: o Privy completa o OAuth, o React Router nao encontra rota para /redirect e
  o utilizador fica numa pagina VAZIA, sem nunca entrar na conta.

═══ CORRECÇÃO ═══
  - Nova rota STANDALONE `/redirect` em App.jsx, FORA do <Route element={<AppLayout/>}>:
    dentro, os gates de cota/LGPD poderiam bloquear a própria página que existe para
    completar a entrada.
  - Componente `EntradaOAuth`: com `ready && isConnected` -> navigate('/', {replace:true});
    sem sessão -> estado de entrada e, ao fim de 6 s, saída MANUAL em <a href="/"> (um
    carregamento novo, que é onde o SDK restaura a sessão). NUNCA página em branco.
  - Decisão em src/lib/retornoOAuth.js (pura, testável).

═══ TESTE + MUTAÇÃO ═══
  src/lib/retornoOAuth.test.mjs (5 testes). Dois leem a FONTE:

    - as duas pontas têm de coincidir: ROTA_RETORNO_OAUTH == o path do
      customOAuthRedirectUrl do PrivyRoot (se alguém mudar uma, o teste avisa)
  TDD: o teste da rota foi escrito ANTES da rota e deu RED ("não há <Route path=\"/redirect\">

  Mutação: M5 remove a rota -> RED; M6 "nunca navega" -> RED; ambos restaurados idênticos.

  ⚠️ Nenhum teste de componente podia apanhar isto: o App.jsx não é renderizável em teste
