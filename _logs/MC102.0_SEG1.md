# MC102.0 — SEG1: Frente B, CAS no pedido (2026-09-29)

> ⛔ **ERRATA (SEG3, ronda 1).** O `gravar()` descrito abaixo usava `setJSON(…, { onlyIfMatch })`, que na 10.0.0 **não envia o If-Match**. A mutação dava 7/7 porque os **duplos eram mais estritos que a biblioteca real** (aplicavam a condição no `setJSON`). Corrigido em `3730c6c`:
> - `set(chave, JSON.stringify(pedido), { onlyIfMatch })`;
> - escrita confirmada só com `etag`;
> - duplos fiéis;
> - 409/503 no handler;
> - verificação com o cliente real (`scripts/mc1020-cliente-real.mjs`).
>
> Os números actuais são **mutação 10/10** e suíte **469/469 · 745/751**.

**Veredito: SEGUIR.** Desenho (C), por decisão do operador (R18, ver SEG-1).

## 1.1 Linha de base

`gravar(pedido, evento)`: carimba, acrescenta ao histórico, faz `setJSON` sem condição. Os 4 chamadores lêem com `lerPedido()` **antes** (SEG-1 §-1.6).

## 1.2 Correcção (`_lib/pedidos.mjs`)

- **`gravar(pedido, evento, etag)`** (interno, não exportado):
  - `store_indisponivel` sem store;
  - **`etag_indisponivel` sem etag (fail-closed)**;
  - `setJSON(…, { onlyIfMatch: etag })`, e `modified:false` dá `conflito_escrita`.
- **`atualizarPedido(produtoId, mutar)`** (novo, interno): em cada tentativa lê com `getWithMetadata` (etag), corre `mutar(pedido)` sobre o pedido **acabado de ler** e grava. Se `mutar` devolver `{evento}`, grava; senão devolve o resultado (erro de guarda ou idempotente) sem gravar. Retry **só** em `conflito_escrita`, no máximo **`MAX_TENTATIVAS_CAS = 3`** (exportado para o teste). Sem backoff, sem lock, sem fila.
- **Chamadores:** `definirMorada`, `marcarRecebido`, `definirRastreio`, `definirNfe`. As assinaturas exportadas são as mesmas. O corpo passou para dentro de `mutar`, sem alterar as guardas nem os códigos de erro. Um `ValidationError` lançado por `validarMorada`/`validarRastreio`/`validarNfe` continua a propagar como antes.
- **Mudanças de comportamento (declaradas):**
  1. As guardas são **reavaliadas** em cada tentativa. Uma morada concorrente com o envio passa a ser recusada (`pedido_ja_enviado`) em vez de ser gravada depois do envio.
  2. `definirRastreio`/`definirNfe` **só notificam se a escrita teve sucesso**. Antes notificavam sempre, mas o ramo de falha era praticamente inalcançável: sem store, o `lerPedido` já devolvia `pedido_nao_encontrado`.
  3. Dois códigos novos, `conflito_escrita` e `etag_indisponivel`, que não estão no mapa `erroDe` do handler. Caem no default **400**. Mudar o mapa para 409/503 exigiria tocar em `pedidos.mjs` (handler), que o MC não autoriza. **Pendência para o operador.**
- `lerPedido` continua a servir os GET, sem alterações.

## 1.3 Duplos de teste

Em `mc102-recebido`, `mcecommerce01a-pedidos` e `mcecommerce01a-ponte`, cada duplo de `getStore` ganhou:
- `getWithMetadata` (etag = sha1 do conteúdo);
- `setJSON(k, o, opt)` que **recusa como o servidor**: etag diferente ou chave ausente → `{modified:false}`;
- **ignora um `onlyIfMatch` falsy**, como o cliente real, para não esconder uma escrita incondicional.

A API existente do duplo (`get`/`setJSON`/`list`/`delete`, `falhaChave`, `blobsRebentam`) não mudou. Os 42 testes existentes destes ficheiros passam.
