### 1.2 — Onde vive o CSP

### 1.3 — ⚠️ PREMISSA CORRIGIDA: os clientes Supabase

O enunciado diz «o app cria múltiplos clientes Supabase». **Medido: existe UM único sítio a
criar cliente** (`src/lib/supabaseClient.js:29`), e já era um singleton *lazy*.

A causa real é outra, e é mais interessante: **o singleton guardava o VALOR resolvido dentro
de uma função `async`.**

```
let _client = null;
export async function getSupabaseBrowser() {
  if (_client) return _client;              // ← guarda
  const { createClient } = await import(...) // ← JANELA: aqui o _client ainda é null
  _client = createClient(...);
```

Dois chamadores no mesmo tick passam **ambos** o `if` antes de qualquer um escrever. E há
exactamente dois, ambos em effectos de montagem: o `ligar()` do realtime
(`useRealtimeConfig.js:56`) e o `carregarRecursos()` (`useRecursosApp.js:80`).
**É daqui que vem o «Multiple GoTrueClient instances»** — e não de dois `createClient`.

### 1.4 — ⚠️ PREMISSA CORRIGIDA: o hook do realtime

O enunciado aponta `useRecursosApp` como o sítio do bug de subscrição.
**Medido: `useRecursosApp.js` não subscreve nada** — só faz um `select` pontual e cai em
fallback para a Netlify Function. Quem subscreve é **`src/hooks/useRealtimeConfig.js`**.

E aí a **ordem está CORRECTA** (`L58-74`): `.channel(...).on(...).subscribe(...)`. O HARD
GATE 6 já estava satisfeito no papel.

**A causa do erro é outra, e está no reconnect:**

```
const limparCanal = async () => {
  if (!canal) return;
  try { const sb = await getSupabaseBrowser(); sb?.removeChannel(canal); } catch {}  // ← SEM await
  canal = null;
};
```

`sb.removeChannel()` é **assíncrono** e não era aguardado. O `supabase-js` **deduplica canais
por topic**: `sb.channel("config_remota:X")` devolve o canal **existente** se esse topic ainda
estiver vivo. Sequência de produção:

1. o canal cai (`CHANNEL_ERROR`/`TIMED_OUT`) → `reagendar()`;
2. ao fim do backoff: `await limparCanal()` → dispara `removeChannel` **e segue**;
3. `ligar()` pede logo `sb.channel("config_remota:X")` → **recebe o canal antigo, ainda
   subscrito**;
4. `.on("postgres_changes", ...)` sobre um canal já subscrito →
   **«cannot add `postgres_changes` callbacks after `subscribe()`»**.

Ou seja: o erro de produção **não é uma ordem errada no código — é uma corrida temporal**.
Corrigir a ordem (o que o enunciado pedia) não teria mudado nada.

### 1.5 — Reprodução em produção

Os 3 erros foram observados na consola (screenshots do operador, 27/09). A reprodução
automatizada em headless **não foi feita** nesta sessão: exige uma sessão com
`VITE_SUPABASE_*` activos e o gate LGPD aceite. Fica declarado — e é a razão pela qual a
validação em produção no SEG4 assenta no header medido por `curl` e não só na consola.

Seguir com os 3 problemas — mas **corrigindo as causas medidas**, não as do enunciado:

**realtime = aguardar a remoção** (não «trocar a ordem»).

## SEG0 — CSP

`netlify.toml` → `connect-src` ganha **`https://*.supabase.co`** (REST) e
**`wss://*.supabase.co`** (WebSocket do Realtime), inseridos logo após `'self'`.

**HARD GATE 4 preservado e agora guardado por teste:** nenhum wildcard genérico. A guarda
varre `connect-src`, `script-src`, `default-src`, `frame-src` e `img-src` e só aceita
wildcards de subdomínio **com esquema** (`https://*.dominio.tld`); recusa `*`, `https://*`,
`*.com`. **Mutação M2 prova que a guarda morde** (abrir o CSP todo → RED).

## SEG1 — Singleton verdadeiro

`src/lib/supabaseClient.js`: o cache passa de **valor** (`_client`) a **promessa**
(`_promessa`). A 2.ª chamada concorrente recebe a **mesma promessa em voo** → a janela fecha →
um só cliente.

Dois detalhes que importam:

- **A assinatura não mudou para os chamadores.** Continua a devolver algo que se `await`a
  (`Promise.resolve(null)` no caso sem config), pelo que `await getSupabaseBrowser()`
  funciona igual nos 4 sítios que o usam. Zero alterações fora deste ficheiro.
- **Falha de import não envenena o singleton:** o `.catch` solta a `_promessa` para permitir
  nova tentativa. Um singleton que morre para sempre no primeiro erro de rede é pior que o
  problema que veio resolver.

## SEG2 — Realtime

`useRealtimeConfig.js`: `await sb?.removeChannel(c)` — a correcção real — mais um detalhe de
reentrada: `canal = null` **antes** do await, para que duas limpezas concorrentes não removam
o mesmo canal duas vezes.
