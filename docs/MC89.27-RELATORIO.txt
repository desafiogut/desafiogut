MC89.27 — ELIMINAÇÃO DEFINITIVA DA MENSAGEM SEPOLIA
Relatório final · 2026-07-31
================================================================================

VEREDITO (R8): CUMPRIDO.
A mensagem "⚠️ Ambiente de teste — rede Sepolia · contrato não configurado"
desapareceu do APK, verificada no DOM vivo do aparelho, com controlo negativo.

--------------------------------------------------------------------------------
1. A DESCOBERTA QUE MUDOU O PLANO
--------------------------------------------------------------------------------
O enunciado pressupunha um defeito a corrigir. Não era.

A mensagem NÃO era um bug — era o alarme do MC88.25 a funcionar exactamente
como foi desenhado. O APK do MC89.26 estava, de facto, configurado para
Sepolia e SEM contrato. O aviso dizia a verdade.

Isto inverte a correcção certa. As três "soluções" que o enunciado admitia —
ajustar o código que gera a mensagem, mexer no default de network.js, ou fazer
network.js aceitar VITE_CONTRATO_MAINNET — teriam apagado o alarme e deixado
o defeito. O resultado seria um APK sem RPC de mainnet e sem contrato, agora
silencioso: a recriação exacta do MC88.24 ("o PIX debitou e a senha não
creditou"), mas sem nada na tela a denunciá-lo.

Por isso AvisoRede.jsx e src/lib/network.js NÃO foram tocados.

--------------------------------------------------------------------------------
2. CAUSA-RAIZ
--------------------------------------------------------------------------------
O APK do MC89.26 foi compilado com `npm run build` (Vite puro), que lê os
ficheiros .env do DISCO. O disco tinha apenas:

    VITE_CONTRATO_MAINNET=0x0052477A…16cd     ← variável que NENHUM código lê
    VITE_NETWORK_STAGE=mainnet

src/lib/network.js lê VITE_CONTRATO_SEPOLIA (não …_MAINNET) e faz
`Number(VITE_CHAIN_ID ?? 11155111)`. Sem essas duas variáveis:

    CONTRATO     = ""         → "contrato não configurado"   (AvisoRede L30)
    CHAIN_ID_DEC = 11155111   → "rede Sepolia"               (AvisoRede L28)
    STAGE        = "mainnet"  → não dispara                  (L29 silente)

Os dois ramos que dispararam, e o terceiro que não disparou, batem certo com o
texto observado no ecrã. Assinatura exacta, sem ambiguidade.

O env do Netlify em produção estava — e está — CORRECTO. Nunca foi injectado
porque o comando usado não o injecta.

--------------------------------------------------------------------------------
3. POR QUE A LIMPEZA MANUAL DO BUNDLE NÃO PODIA FUNCIONAR
--------------------------------------------------------------------------------
A substituição manual no dist trocou ocorrências de um endereço. Mas o defeito
eram duas variáveis AUSENTES — não havia `VITE_CHAIN_ID:` no ficheiro para
substituir. Não se corrige uma ausência com find & replace. A configuração de
rede resolve-se em tempo de build, não em tempo de execução.

--------------------------------------------------------------------------------
4. O QUE FOI ALTERADO (R1 — mínimo)
--------------------------------------------------------------------------------
Código-fonte rastreado alterado: NENHUM.
   `git status -- desafio-gut/frontend/src` devolve vazio.

Alteração 1 — processo de build
   `npm run build` → `npm run build:apk`
   (netlify build --context production && validar:dist && cap sync android)

Alteração 2 — desafio-gut/frontend/.env (ficheiro gitignored, .gitignore:21)
   Removido `VITE_CONTRATO_MAINNET`, variável que nenhum código lê e que dava
   a ilusão de um disco configurado para mainnet. Era essa falsa confiança que
   tornava `npm run build` plausível. Substituída por um comentário que aponta
   para o comando correcto. Zero impacto em runtime: era código morto.

6. VALIDAÇÃO (R7 — cada segmento verificado)
--------------------------------------------------------------------------------
Prova estática — diagnosticar() minificada no bundle:
   k=1, dn=1 → k!==dn falso · un="mainnet" → falso · A=0x0052…16cd ≠ fn → falso
   ⇒ pn() devolve []  ⇒  mn() devolve null  ⇒  nada renderiza.

Prova viva — CDP contra a WebView do APK instalado (adb forward + WebSocket
nativo do Node; o MCP chrome-devtools não anexa a alvo remoto):
   /admin autenticado como 0x1E1bAe7F…d198cB → temAvisoTeste false, role=status []
   / após arranque limpo                      → temAvisoTeste false, role=status []
   screenshot da raiz                          → rodapé sem a pílula vermelha

Controlo negativo — banner falso injectado no DOM vivo:
   COM  → temAvisoTeste true, roleStatus ["⚠️ Ambiente de teste — rede Sepolia…"]
   SEM  → temAvisoTeste false, roleStatus []
   A sonda deteta quando deve. Os "false" são negativos reais.

--------------------------------------------------------------------------------

Será preciso voltar a entrar. Nada no servidor nem on-chain foi tocado.

--------------------------------------------------------------------------------
9. RISCO RESIDUAL E RECOMENDAÇÃO
--------------------------------------------------------------------------------
O gate `validar:dist` só corre dentro de `npm run build:apk`. Quem correr
`npm run build` seguido de `npx cap sync android` à mão contorna-o e reproduz
este MC. O .env já não engana, mas isso é uma defesa fraca — o ficheiro é
local e não commitável.

Recomendação (fora do escopo deste MC, R1): tornar o gate inevitável, ligando
a validação ao próprio `cap sync` em vez de a deixar num script paralelo.
Decisão do operador.
