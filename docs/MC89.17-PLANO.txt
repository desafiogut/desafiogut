## 1. DIAGNÓSTICO

### O que já existe (LEITURA)
- `_lib/notificacoes-usuario.mjs`: Blob `notificacoes:{endereco}`, FIFO 50, fail-soft.
  `adicionarNotificacao(endereco, notif)` — escreve. `lerNotificacoes(endereco)` — lê.
  `marcarLidas(endereco)` — atualiza. Tipos: lance_unico, perdeu_exclusividade,
  voce_venceu, edicao_encerrada.
- `notificacoes.mjs` (GET, admin-gated): lê eventos DERIVADOS de várias fontes
  (edições, lances, sistema) e devolve notificações agregadas. NÃO é emissão —
  é o consumidor que lê.

### O que NÃO existe
- Emissão pelo admin via endpoint HTTP
- Qualquer integração SendGrid no backend (`@sendgrid/mail` não está em package.json)
- Qualquer integração Twilio no backend
- Qualquer integração FCM/Firebase
- Tabela `notifications` no Supabase
- Tabela `notification_templates`
- Histórico de envios do admin
- Agendamento

## 2. PLANO (execução no MC89.17, 2-3 sessões)

### S1 — Canal in-app (o que funciona hoje, sem dependências novas)

**Tabela `notifications`** (histórico agregado, Supabase):
```sql
CREATE TABLE notifications (
  id uuid PK DEFAULT gen_random_uuid(),
  canal text NOT NULL,          -- inapp | email | whatsapp
  destino text NOT NULL,        -- todos | admins | especifico | segmento
  destino_ids jsonb,            -- [endereco, ...] quando especifico
  titulo text,
  mensagem text NOT NULL,
  link text,
  agendado_para timestamptz,    -- NULL = já
  criado_por text NOT NULL,
  criado_em timestamptz DEFAULT now(),
  status text DEFAULT 'enviado', -- enviado | agendado | falha
  total int DEFAULT 0,
  entregues int DEFAULT 0
);
```

**Endpoint POST /admin-notify**:
- Canal: "inapp" (único que funciona hoje; email/whatsapp respondem 501)
- Destino: "todos" resolve via vw_utilizadores; "admins" resolve via admin-list;
  "especifico" aceita lista de endereços
- Para cada destinatário, chama `adicionarNotificacao(endereco, notif)`
- Regista em `notifications` (histórico) + `admin_logs` (auditoria)
- Gate: admin+. RL: 10/min.

**Endpoint GET /admin-notifications**:
- Histórico de envios da tabela `notifications`
- Paginação por cursor. Gate: operador+.

## 3. O QUE FICA PARA DEPOIS

- **E-mail (canal real):** depende de @sendgrid/mail no backend. MC próprio ou
  executado junto com o canal in-app se as dependências não forem bloqueantes.
  A UI já está preparada (o dropdown mostra "E-mail" e o backend responde 501
  com "não configurado" até o módulo existir).

- **WhatsApp:** depende de credenciais Twilio no backend. MC próprio.

- **Push (FCM):** projeto Firebase + google-services.json + rebuild do APK.
  A UI mostra "Push — em breve" desabilitado.

- **Templates:** tabela `notification_templates` + UI de gestão. MC próprio.

- **Agendamento real:** a tabela `notifications` já tem `agendado_para`. Um
  cron `notificacoes-scheduled.mjs` lê os agendados e envia. MC próprio.

## 4. RISCOS

- R-1 (BAIXO): e-mail alcança 3 pessoas. A UI explica-o; não é defeito.
- R-2 (MÉDIO): `adicionarNotificacao` escreve em Blob (fail-soft). Se os Blobs
  estiverem cegos, a notificação é "enviada" mas nunca chega. Mitigação:
  o status `entregues` só é incrementado quando a escrita no Blob confirma,
  e o endpoint `admin-notify` reporta quantos foram realmente escritos.
- R-3 (BAIXO): não há fila para envio em massa para "todos". Com 7 utilizadores
  é irrelevante; com 1000 seria um problema. Solução futura: usar `fila_tarefas`.
