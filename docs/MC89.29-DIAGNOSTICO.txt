================================================================================
4. PORQUE O PLANO ORIGINAL DO MC89.29 NÃO É APLICÁVEL
================================================================================
O enunciado propunha criar .env.local com contrato/chainId/RPC fixos e compilar
com `npm run build`. Três problemas objectivos:

  a) `npm run build` = "vite build" puro. Lê os .env do DISCO e ignora o env do
     Netlify. É exactamente o caminho que causou o MC88.22/88.23/88.24 (APK a
     ler contrato abandonado; utilizador pagou o PIX e o saldo não apareceu).
     O próprio enunciado proíbe-o na regra R10, mas pedia-o no passo 2.1.

  b) Declarar a config de rede em .env.local torna o guarda validar-dist-rede.mjs
     permanentemente cego: passaria a validar o disco local, não o env real de
     produção. Se o Netlify voltar a driftar, ninguém repara. O ficheiro .env
     actual documenta esta decisão (MC89.27) por escrito.

  c) .env e .env.local estão em .gitignore (linhas 21-22). O commit pedido em 1.5
     ("git add .env.local") não pode existir; e forçá-lo publicaria a chave
     Alchemy no repositório — viola R4/R5.

O ficheiro .env do disco NÃO é apagado: contém apenas VITE_NETWORK_STAGE=mainnet
e o comentário do MC89.27 que impede a reincidência.
