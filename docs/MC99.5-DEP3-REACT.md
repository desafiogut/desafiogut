## Detalhe e evidência

### DEP3-01 — *Gate* do `authToken` (a única waterfall real, e é estrutural)

Não existe neste código o padrão clássico "dois pedidos independentes em série". Os 212 `await` foram filtrados por dependência (um `await` só conta como waterfall se o seguinte **não** usar nenhuma variável do anterior); sobrou **1 par**, em `lib/adminAuth.js:261→264`, e é um *refresh-then-retry*:

```
261|  const ok = await renovar();
264|  resp = await fetch(url, { ...init, headers: cabecalhos });   // re-tenta depois de renovar
```

A waterfall que existe é outra, e é a categoria nº 1 da Vercel (`async-dependencies`): **um recurso partilhado que todos os ecrãs esperam**.

- `AppContext.jsx:887-918` — `obterAuthToken()`: `getEthereumProvider()` (893) → `getSignerFromProvider` (894) → `signer.signMessage` (895) → `POST /.netlify/functions/auth-user` (896) → `.json()` (908). Quatro `await` em série, dos quais três são locais (Privy/ethers) — o custo real é **1 RTT**.
- Esse token só é pedido **depois** do primeiro render, com atraso programado (`AppContext.jsx:944`, `setTimeout`), e o efeito re-corre por tentativa (`AppContext.jsx:929-949`).
- Enquanto ele não existe, **17 efeitos em 10 ficheiros** estão na rua com `if (!authToken) return`:
  `AppContext.jsx:513, 865, 949, 1010, 1017, 1052, 1081, 1106` (8 sítios), `ChatbotWidget.jsx:436`, `PainelIndicacao.jsx:60`, `ReferralRegistrar.jsx:117`, `WalletCard.jsx:60`, `CorporativoAnalytics.jsx:52`, `CorporativoBanners.jsx:62`, `CorporativoCarteira.jsx:95`, `CorporativoCotas.jsx:48`, `CorporativoDashboard.jsx:157`.
- O próprio repositório já mediu o custo desta cadeia: «Fecha os 1 889 ms de Dashboard comum medidos no login fresco» (`AppContext.jsx:1375`), e «o valor correcto era pintado aos ~2,0 s, apagado aos ~3,3–4,4 s, e repintado igual aos ~5,2–6,6 s» (`AppContext.jsx:967-968`).

**Porque não é um `Promise.all`:** a assinatura tem de existir antes do token, e o token antes de qualquer `/cotas`. Não há aqui trabalho independente para paralelizar. O ganho possível é (a) encurtar a cadeia de espera do token (uma chamada em vez de duas quando o token está em `sessionStorage`), e (b) deixar os efeitos que **não** precisam de identidade (ex.: `/produtos` público, edições) arrancarem sem esperar pelo token. É por isso que a classificação é **Impacto Alto / Esforço M / Risco Médio**, e não um "põe `Promise.all`".

- **60 chaves** no objecto (`AppContext.jsx:1317-1388`).
- **37 chamadas `useAppContext()`** em **34 ficheiros** — todas re-renderizam quando a identidade do `value` muda, mesmo que só consumam `authToken`.
- No mesmo ficheiro há **1** `useMemo` — e está no `TimerProvider` (linha 1429), não no valor.

Uma correcção de memoização aqui tem de declarar as dependências com o mesmo rigor, ou transforma um problema de re-render num problema de dados obsoletos.

### DEP3-03 — O monólito `AppContext.jsx`

1 435 linhas, **28 `useState`**, **26 `useEffect`**, 8 `useCallback`, **8 efeitos com IO**, 10 sítios `apiGet/apiPost/fetch`, 3 pollings activos (`setInterval(refetchSaldo, 30000)` L877; `setInterval(refetchSaldoRs, 5000)` L1015; notificações 2 s/10 s L1096-1098; on-chain 60 s L1130) e um tick de 250 ms (L1190). Interface pública: 60 chaves.

**Medido e deliberadamente não sinalizado como defeito:** o tick de 250 ms **não** é uma tempestade de re-renders — está guardado (`L1162-1202`: só faz `setState` quando `restante === 0` ou quando `encerrado` muda), e o polling de 5 s reescreve primitivos iguais (`L1003-1004`: `setSaldoRsCentavos(centavos)`, `setSaldoRsStatus("ok")`), onde o React desiste do render por `Object.is`. O defeito não é a frequência: é **qualquer** dos 28 campos invalidar o mesmo objecto de 60 chaves para 37 consumidores.

O precedente certo já existe no ficheiro: o `TimerProvider` (L1396-1434) foi separado **precisamente** para o tick não tocar no `AppProvider` (comentário MC44 P0). O mesmo raciocínio aplica-se a `saldoSenhas`/`notificacoes`/`cotaCorporativa`.
